# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ffbot` is a local web GUI (`scripts/gui.py`, port 8321) live-synced to one Sleeper fantasy football league: a draft room with live pick sync, and a read-only weekly manager that auto-loads the current week's real roster/lineup/waiver state. Terminal CLIs (`scripts/draft.py`, `scripts/week_report.py`) share the identical engine, draft log, and lineup state as fallbacks — see [docs/REFERENCE.md](docs/REFERENCE.md) for those and the full config reference; [docs/GUIDE.md](docs/GUIDE.md) is the day-to-day GUI walkthrough. Everything is read-only against Sleeper's public, unauthenticated API — permanently advisory, since Sleeper has no write endpoint at all. The shipped `config.yml` is live-by-default (`projection_source`/`roster_source`/`standings_source`/`league_rosters_source`/`board_points_source` all set to `sleeper`); the code-level dataclass defaults in `ffbot/config.py` are offline, used only when a key is deleted entirely.

## Architecture

- **`ffbot/sleeper/`** — the read-only, unauthenticated HTTP client for Sleeper's public API (`SleeperClient`, stdlib `urllib` only). Documented endpoints (state, user, leagues, rosters, users, matchups, drafts, players, trending) are stable; two undocumented ones (season projections/ADP, ownership%) are unsupported by Sleeper and every caller must treat a fetch failure as "no data this run." Per-endpoint TTL cache (`cache.py`); `draft()`/`draft_picks()` are never cached (a live draft poll needs real-time reads). `models.py` translates Sleeper's word-based injury status onto this repo's existing single-letter vocabulary.
- **`ffbot/live/` + `ffbot/markets/`** — two more no-auth live clients feeding the weekly outside-data signals: `live/schedule.py` (real NFL schedule, always refetched), `live/weather.py` (Open-Meteo forecast), `live/conditions.py` (merges both plus Kalshi odds with `weekly/week-NN.yml` research field by field — research wins for kickoff, venue and Vegas totals; the live forecast wins for weather, see the invariant below). `markets/kalshi.py`/`kalshi_nfl.py` are the raw and NFL-semantic Kalshi clients (game odds are always live; per-player prop markets are gated on `use_untested_features`). Every fetch here degrades independently with a surfaced alert, never a crash.
- **Core engine** — `ffbot/models.py` (the `Player` shape and status/slot vocabulary, tracing back to this project's original Yahoo target but unchanged since Sleeper translates onto it at the boundary), `ffbot/lineup.py` (the deterministic, exactly-optimal bipartite-matching lineup optimizer — see the design invariant below), and `ffbot/policy.py` (drop guardrails: undroppable flags, ownership/draft-round protection, temporary-unavailability refusal).
- **`ffbot/form.py` + `ffbot/live/form.py`** — the five FORM signals (usage/momentum/divergence/volatility/upside) as PURE math over a game log, plus the live feed that computes them each run from Sleeper's own realized weekly stats. `ffbot/history/signals.py` feeds the identical math from nflverse for replay; one implementation, two feeds, asserted structurally (`tests/test_live_form.py::TestBothFeedsShareOneImplementation`).
- **`ffbot/demand.py`** — the third no-auth live client family: what OTHER managers are doing about an unrostered player (rivals' failed claims from the league transaction log, Sleeper's global trending adds, the week-over-week ownership delta). Pure, like `ffbot/availability.py`; `report.load_everything` fetches and hands the payloads in, with three independent try/excepts so one source failing costs the others nothing.
- **Weekly path** — `ffbot/week.py` (status overrides, weather/Vegas/venue adjustments, the volatility/upside-lean variance pair), `ffbot/gameplan.py` (the unified weekly recommendations engine behind both the GUI and `week_report.py --waivers` — one pool, one coherent plan, streaming/denial folded in as reasons not categories), `ffbot/denial.py` (tactical denial, threat scored by playoff-bubble seed distance — and, via its fungibility-discounted `denial_value`, the "claim now vs. wait for free agency" term on both waiver and stream rows), `ffbot/roster_source.py` (roster.yml parsing + lineup-state persistence), `ffbot/sleeper_roster.py` (the live-Sleeper roster route), `ffbot/report.py` (`load_everything`, the shared loader with one alert list per live seam), `ffbot/webapi.py` (GUI JSON serializers), `ffbot/week_log.py` (the per-run JSON recommendation record — the weekly analog of `ffbot/draft_report.py`), `ffbot/week_grade.py` (reads those records back after the games and grades each adjustment family against real points — descriptive only, nothing in `ffbot/` imports it), and `ffbot/notify.py` (the one OUTBOUND live seam — push notifications for `scripts/autorun.py`), and `ffbot/research.py` (unattended research — a headless Claude Code run of `.claude/commands/research-week.md` that writes `weekly/week-NN.yml` before a scheduled check reads it, under code-enforced guardrails).
- **Draft path** — `ffbot/board.py` (frozen pre-draft board: FantasyPros CSV loading with graceful missing-file handling, derived replacement level, VOR/tiers, the live Sleeper points overlay applied strictly after league scoring), `ffbot/draft.py` (pick math, ADP survival, `DraftState`), `ffbot/edge.py` (contrarian valuation terms, every weight a fraction of the per-pick decision scale), `ffbot/draft_ui.py` (pure state machine shared by the terminal and GUI), `ffbot/draft_sync.py` (live Sleeper pick sync, main-thread-only `DraftState` mutation), `ffbot/names.py` (two deliberately separate matchers: strict pre-draft ID reconciliation vs. permissive live search), and `ffbot/intel.py` (researched `draft/intel.yml`).
- **`ffbot/history/` + `ffbot/backtest/`** — point-in-time replay against real NFL seasons, for validating tuning/edge weights against outcomes instead of judgment alone. `history.index.as_of()` is the single point-in-time boundary (never fetches a results-bearing source); `backtest/` may read realized outcomes only through `history.actuals.week_actuals`. See [docs/dev/BACKTEST.md](docs/dev/BACKTEST.md) for the full design and [docs/dev/SPICE.md](docs/dev/SPICE.md) for the evidence behind each dial's shipped value.
- **`ffbot/training.py` + `ffbot/training_export.py`** — synthetic draft situations (frozen `webapi.draft_state_json()` snapshots from mock drafts with bots in every seat) exported as a standalone HTML page a human reviewer opens with no server, for a second, high-volume source of judgment on recommendations. Grading reuses `ffbot/draft_report.py`'s `taken_block` so a training verdict and a real draft-report entry are never two different shapes for the same thing. See [docs/dev/TRAINING.md](docs/dev/TRAINING.md) for the tool and [docs/dev/TRAINING-FINDINGS.md](docs/dev/TRAINING-FINDINGS.md) for what it has actually found (its in-season twin is [docs/dev/INSEASON-FINDINGS.md](docs/dev/INSEASON-FINDINGS.md)) and the backtest cells that are queued behind it; every finding it surfaces is a hypothesis, not a change, until `scripts/backtest_draft.py` agrees.
- **`scripts/` + `web/`** — thin shells around the packages above. `scripts/gui.py` is single-threaded on purpose (one shared, mutable `UiState`, no lock). `scripts/schedule_autorun.py` wraps Windows Task Scheduler (or prints the `cron` equivalent) to run `scripts/autorun.py` on a recurring interval. `web/draft_render.js` holds the recommendation-table/roster/opponents rendering shared between the live draft room (`web/draft.html`) and the offline training-pack reviewer (`web/train.html`).

Module docstrings carry the detail this section used to — read the file itself for exactly how a given piece works.

## Design invariants worth preserving

- **Config, not code, for tuning.** New thresholds/weights belong in `config.yml` + the corresponding dataclass in `ffbot/config.py`, not hardcoded.
- **The optimizer must stay exact and deterministic.** Any change to `ffbot/lineup.py` should preserve: (1) exact optimality (not a heuristic), (2) stable output across runs (ties break on player name), (3) the flex-seating rule, and (4) minimal-move preference among assignments the seating rule cannot separate. Both the in-season path and the draft assistant depend on this. A `Player.game_locked` player (his game has kicked off; Sleeper won't move him) is held where he is — a locked starter's slot is pinned and removed from the matching, a locked bench/IR player is never a candidate, and neither ever produces a `Move` — so all four properties hold over the unlocked subproblem, and with nobody locked the output is identical to the lock-free algorithm (`tests/test_lineup.py::TestGameLocks`).
- **Seating is a decision, not a formality, and the seating rule outranks minimal-move.** Every perfect matching of the chosen starters scores identically, so points cannot choose between them — but a flex is the only slot accepting more than one position, and a platform locks each player at his own kickoff, so *which* identically-scoring matching you return is a real choice. `lineup._flex_seating_order` makes it: an early-kickoff player is kept out of the flex first (parking him there locks the roster's only versatile slot for the whole week), then the flex goes to the most replaceable starter. Minimal-move was ORIGINALLY the only preference here, and that is exactly why the bug existed: a roster imported from Sleeper arrives pre-seated, so a minimal-move-only pass ratifies whatever was already there and reports no moves — silently endorsing your best player sitting in the flex. Minimal-move survives as the third component of the sort key and via slots comparing by NAME (a shift between two WR slots is not a move). Don't re-promote it above the rule. A move between two starting slots is labelled "no points change" rather than a projection, so a zero-point reseat never reads as churn.
- **Drops are the one in-season action guarded by explicit policy**, not a confirmation step, because the agent is meant to act unattended. New irreversible actions should get the same treatment: a `Verdict`-returning policy function with the reason surfaced, not a silent allow/deny.
- **`scripts/draft.py`, `scripts/week_report.py`, and `scripts/gui.py` must stay importable and runnable with no network at module level.** `ffbot.sleeper`/`ffbot.sleeper_roster`/`ffbot.projections.sleeper` are all imported lazily, inside the function that actually needs them (`_build_sync`, `report.load_everything`'s live branches, `board.load_board_from_config`'s overlay branch) — the offline paths must keep working with no network at all, not just "no credentials." `week_report.py`'s own research step (weather/injuries/Vegas) is deliberately kept *outside* the script entirely, in the `/gameday` command — see `ffbot/week.py`'s module docstring.
- **Every live network call takes an injectable `opener`/client, and every fetch failure degrades gracefully with a surfaced alert — never a silent success and never a crash.** This is the same contract across every live seam in the repo: `ProjectionSourceConfig`'s `"sleeper"`, `RosterSourceConfig`'s `"sleeper"`, `DraftConfig.board_points_source`'s `"sleeper"`, and `ffbot.draft_sync.DraftSync`'s poll loop. A test asserting this must exist for any new live seam, matching `tests/test_history_index.py::TestAsOfLeakageGuarantee`'s pattern of proving it structurally, not just by inspection.
- **Pre-draft ID matching vs. live TUI search are different problems** (see `ffbot/names.py` above) — don't collapse them into one matcher.
- **Season-long valuation always passes `week=None`** to `optimize()` — `draft.need()` is always a season-long decision. `week.waiver_candidates()`/`rank_streamers()` now accept an optional real `week` too, but only to zero/exclude a candidate's *this-week* contribution when they're on bye that week — the rest-of-season side of any blend stays on the season board (or `ros_board`, when live) and must never be zeroed by it. Weekly *lineup* decisions (`week.build_week_brief`) are the one place a real week number was always correct and required.
- **A `Board`'s `points` overlay (`_apply_points_overlay`/`rescale_board_points` in `ffbot/board.py`) must run AFTER `apply_league_scoring`, never folded into the CSV/row merge ahead of it.** A merged-in `stats` field from an untouched source silently lets `apply_league_scoring`'s recompute clobber the overlay's live number right back to the frozen data it was meant to replace — a real bug this repo shipped and caught once already (see `ffbot/board.py`'s docstring on `_apply_points_overlay` and its regression test in `tests/test_board.py`).
- **`scripts/gui.py` is single-threaded on purpose.** The draft session is one shared, mutable `UiState` with no lock — serializing every HTTP request through one thread (`http.server.HTTPServer`, not `ThreadingHTTPServer`) is what keeps `DraftState` main-thread-only (see `ffbot/draft_sync.py`'s existing invariant on this) without adding one. Don't switch it to a threading server without adding real synchronization.
- **`use_untested_features` gates FEATURES, never intensity, and the gate runs LAST.** `SEASON_UNTESTED_DIALS`/`DRAFT_UNTESTED_DIALS` are exactly `{k : level-3 value == 0 and level-4 value != 0}` — the dials level 4 switched on from nothing, not the ones it merely turned up. `tests/test_config.py::TestBaselineAndUntestedToggle` derives that set from the presets and asserts the match, so the pair cannot drift. In `_resolve_block`, the gate applies AFTER explicit per-key overrides: an unticked box forces those dials to exactly 0.0 even when the overlay carries a slider value, which is what makes the checkbox authoritative rather than advisory. Don't "simplify" it by applying the gate before the overrides, and don't fold an evidence-backed dial into the untested set to make a level-4 preset reproducible in one click — that's a slider's job.
- **A waiver claim's cost is ABSOLUTE, never a fraction of the gain it buys.** `week.priority_option_cost` prices a rolling-priority slot from the slot and `week.decision_scale`, and `week.claim_verdict`'s contract is that `claim_cost` does not depend on `gain`. The original form was `priority_value * gain * (1 - p/num_teams)`, which made `claim_cost < gain` algebraically equivalent to a gain-independent predicate — so `HOLD PRIORITY` was unreachable dead code and a +0.6-point DEF sidegrade was typed a CLAIM exactly as readily as a +54-point starting RB. It shipped, and it pushed that +0.6 row to a phone. `tests/test_week.py::TestClaimVerdictEconomics` asserts gain-invariance and reachability structurally, reading `priority_value` from `SEASON_BASELINE` rather than hardcoding it. A HOLD verdict must also be charged NOTHING, or `gameplan`'s `net <= 0` bars delete the row instead of demoting it to an ordinary add — "not worth a claim" must never silently become "not worth mentioning."
- **Only a player ON WAIVERS is ever charged waiver priority.** `ffbot/availability.py` derives each unrostered player's status every run from the league's settings, its transaction log and the kickoffs of this week and last, by Sleeper's own rules: on waivers from his kickoff until the league's next weekly run (`waiver_day_of_week`, Monday = 0, ~12:05am Pacific — `weekly_run_time_et` until the transaction log teaches the real time), a dropped player until the run on his clear date (the later of the two if both), and everyone else — a bye team's player, everyone after the run until his next kickoff — a free agent. `week.acquisition_verdict` is the one place that turns it into economics: a free agent is kind `"add"` at zero claim cost and is baked into the recommended lineup; a waiver player goes through `claim_verdict` and is a `"claim"` or a `"wait"`, and a player whose game has started brings zero this-week points either way. Last week's kickoffs (`Availability.prior_kickoffs`) feed ONLY that rule, never `game_states()` — which is what marks a rostered player `game_locked`; merged in, they would lock the whole roster on a Tuesday. Unknown status (`waiver_status_source: off`, or a failed fetch, with an alert) prices every add as a claim. "Act now" is decided by `AddDropRec.kind`, never by a `claim_note`'s wording — matching note prefixes is how a HOLD-PRIORITY row got seated as "Add & start" on 2026-09-13. Before 2026-09-13 every Sunday free agent read "HOLD PRIORITY, not worth a claim"; from then until 2026-09-15 only a dropped player was ever on waivers, and a Tuesday check called four defenses sitting on waivers free agents.
- **One executable move per slot; the rest are `backups`, never rows of their own.** `gameplan.fold_backups` keeps the best row of a group — every candidate for the same streaming slot, every claim at the same position spending the same drop — and attaches the others as typed `AddDropRec.backups`, best first; the acceptance loop also consumes a stream row's incumbent as a drop key, so a second row naming him can never be accepted. On 2026-09-15 four defenses against one Detroit were accepted as four adds, `post_roster` grew to seventeen on a fourteen-man roster, and the optimizer seated the fourth-ranked one while the list led with the first; `tests/test_gameplan.py::TestOneExecutableMovePerSlot` reproduces it. Claims at different positions that share a drop stay separate rows by design (each is its own "just this one move" scenario).
- **A scheduled check has a purpose, and its message is shaped by it (`Trigger.kind`).** Pre-kickoff is lineup-first. The Tuesday waiver-claims check carries your priority, each claim with its backups, and what to leave for free agency — never a lineup line; the Wednesday free-agent check carries what happened to your claims and the free agents worth adding, each with where he starts. A quiet check says so (`waiver_heartbeat`/`post_waiver_heartbeat`/`look_heartbeat`) under `notify.heartbeat`. Every slot lives in `config.yml`'s `autorun:` block; the CLI flags override, so the registered task needs no re-registration. The manager's calls, 2026-09-15.
- **A due-diligence look (`kind == "look"`, `autorun.looks`) is a look at the ROSTER that researches first, never a research report.** The Friday slot was born as the research pass and pushed `research_line` ALONE — no lineup, no adds — so across two weeks of a season no evening push ever carried a decision: on 2026-09-18 it said "no official status changes" while the plan underneath it wanted Swift started over Judkins. A look now sends the same lineup-first `actionable_summary` a pre-kickoff check does, because the action is the same action, and `looks` is `{weekday: local hour}` so the manager can add or move a slot without a code change (shipped: `{fri: 19, sat: 18}`, 2026-09-19 — Friday after the last game-status report files, Saturday after the 4pm ET elevation deadline and inside the 24 hours where a forecast is worth acting on). `research.injury_report_*` survives only as the legacy single slot, read when `looks` is empty. Each look carries the next kickoff WINDOW (never a research `slot` — that reads `kind`) so a quiet one can name the starters who lock first; `_lock_lines` is shared with `heartbeat_message` so a look and a pre-kickoff check can never disagree about who is already frozen.
- **A weekly projection shown to a human is the number the Sleeper app shows, and every change we make to it is named.** Sleeper-sourced rows carry their raw stats (`sleeper_stats`) and are scored by `scoring.score_sleeper_stats` against the league's own `scoring_settings` (live every run; `league.yml`'s `sleeper_scoring_settings` is the offline copy) — Sleeper's arithmetic, not a `StatLine` approximation, which on 2026-09-13 had kickers +2.9 high (an averaged FG-distance mix paid for unbanded makes Sleeper pays nothing for) and a defense −1.0 low (a fractional points-allowed missing its bucket). Weather/Vegas/trend adjustments still drive the optimizer, but `PlayerMetrics` carries `sleeper_proj` beside `week_proj` and each step's delta (`week.adjusted_players_with_breakdown`), rendered "Sleeper 18.9 · ours 15.2 (wind 40 mph −3.9)" — a 21% wind cut once hid inside the only number displayed. Real points for started games (`LoadedReport.live_points`) are descriptive only, like `season_ptd`; a rostered player whose game has kicked off is `Player.game_locked` and `policy.can_drop` refuses him, because Sleeper won't allow the move.
- **The noise floor is in points per week.** `policy.can_claim(week_gain, ros_gain_per_week, …)` clears a move when either horizon beats `noise_floor_weight * decision_scale / predictiveness[pos]`; it used to compare the dimensionless blend. A forced need (K/DEF on bye/OUT) is exempt, a floored row is noted rather than silently dropped, and a sub-floor start/sit swap between rostered players keeps the optimizer's order but is labelled a toss-up.
- **No displayed recommendation number is the ros/week blend.** `value`/`net` are `ros_blend * (a rest-of-season TOTAL) + (1 - ros_blend) * (ONE week's points)` — an average of two scales differing by ~17x, which denominates nothing. It is the internal ranking key and is labelled `rank key … (blend)`; everything shown to a human is points per week (`DecisionMetrics.week_gain` and `ros_gain_per_week`, rendered by `week_report._per_week_strip`). Presenting the blend as points is how a move worth +0.2 points read as "+0.6" and got notified. New numbers behind a recommendation go on `DecisionMetrics` in a stated unit.
- **A streaming position's gain is weighted less on rest-of-season value, but never zero** (`SeasonConfig.stream_ros_blend`, 0.25 against `ros_blend`'s 0.5). Rest-of-season value is something you ACQUIRE and at a streamed position you never do — the counterfactual is "whatever DEF is best next week", not "no DEF". But 0.0 was tried and INVERTS the board: it ranked a tier-4 defense (rest-of-season −2.0/wk) above a tier-3 one for a +1.2-point weekly matchup edge. You still have to hold whoever you pick up, and the tool recommends one move, not a season of churn.
- **In-season valuation reads only live weekly and rest-of-season projections, never the draft board.** `gameplan.valuation_pool` is the one pool every weekly consumer reads (the plan, roster status, streamer ranks, the matchup lean). Under `projection_source: sleeper` it is the ROS board built with `board.rescale_board_points(..., live_only=True)`: a player without a live projection is dropped and no ADP or draft intel is carried. A failed ROS fetch skips waiver and streaming valuation with a note, never falls back to draft-board numbers; a rostered player with no live projection lands in `roster_board_keys`' `missing` and out of drop/hold math. The draft board remains only the player-list scaffold and the pool for offline configs. When this landed, 206 of 686 in-season pool players had silently kept draft-board totals, 13 of them kickers the stream scan compares.
- **Unattended research may write only the week file, and only an official source can set a `status`.** `ffbot/research.py` runs headless Claude Code under `--permission-mode dontAsk` with an allow-list of web search/fetch, Read, and Edit scoped to `weekly/week-NN.yml` (`Edit(path)` covers Write; a `Write(path)` rule is rejected by the CLI and cost week 2's pre-waiver research) — never widen it and never use `bypassPermissions`. A researched `status` overrides Sleeper's live one with nobody reviewing it before a check runs, so the official-source rule (`ResearchConfig.official_source_domains`) is enforced in code after every run rather than trusted to the prompt; a write that fails validation is rolled back byte-for-byte; and a slot pass never deletes another slot's entries. `tests/test_research.py` proves each structurally. Research stays OUTSIDE `week_report.py`: `scripts/autorun.py` orchestrates it, and the report only ever reads the file.
- **Live forecast weather outranks researched weather.** `live.conditions.merge_conditions` merges field by field: for `wind_mph`/`precip_pct`/gusts/temp the Open-Meteo forecast wins whenever it has a reading and research only fills a gap, with a surfaced alert on a large disagreement; for everything else research wins. It was whole-entry research-wins until 2026-09-13, when research turned a storm-*gust* note into `wind_mph: 40` for JAX–CLE (the forecast had ~6), the 21% cut pushed "bench Trevor Lawrence", and he scored 26. Research reads prose about weather; the forecast is the number. `tests/test_live_conditions.py::TestMergeConditions::test_jax_cle_2026_week_1_regression` pins it.
- **A projection grade proposes; it never tunes.** `scripts/autorun.py` runs `scripts/grade_week.scheduled_grade` every Tuesday morning (`config.yml`'s `grade:`): last week's grade, per-game evidence across the season, and a named dial only when an adjustment family clears `min_weeks`/`min_games` with an interval excluding zero. Evidence is counted per GAME (`week_grade.game_key`) because every player in a game shares its weather and line — week 1 of 2026's four bad wind rows were one bad researched number, and an auto-tuner would have cut `weather_weight` for an input bug. Nothing in `ffbot/` imports `week_grade`, and neither it nor the script writes configuration (`tests/test_week_grade.py::TestDescriptiveOnly`); a proposal is a hypothesis for a backtest, and a human moves the dial.
- **Forward-logging a signal never waits on that signal's weight.** `SeasonConfig.kalshi_forward_log` fetches and writes `data/kalshi_log/` while `kalshi_weight` is 0.0, and merges nothing into valuation. Logging used to sit behind the weight, which `use_untested_features` holds at zero — so the evidence that could ever justify the weight was never collected (INSEASON-FINDINGS W4).
- **`config.yml` is never rewritten by code.** It's hand-narrated with comments a YAML round-trip would destroy. Anything that needs to *write* settings (the GUI's Settings page) writes to the gitignored `config.local.yml` overlay instead (`_deep_merge`d on top at load time) — never add a code path that calls `yaml.safe_dump` against `config.yml` itself.
- **Historical replay must go through `ffbot.history.index.as_of()`.** No backtest code may read a historical data file (`data/history/*.csv`) directly — `as_of()` is the single point-in-time boundary, and its leakage guarantee (never fetching a results-bearing source) only holds if every caller actually goes through it. See [docs/dev/BACKTEST.md](docs/dev/BACKTEST.md)'s leakage register.
- **A rank→points (or any) calibration used for historical projections must be fit on seasons other than the one being graded.** `ffbot.history.projections.ecr_projections` enforces this by raising, not just documenting it — fitting on the test season is the single most likely way to fake a good backtest result.
- **`ffbot/backtest/` may read realized outcomes only through `ffbot.history.actuals.week_actuals`, never `WeekSnapshot.game_rows` directly.** `game_rows` is `ffbot.history.index`'s own separate post-hoc-scoring channel; routing every grading read through one function keeps "did a decision accidentally see the answer" a one-place-to-check question.
- **Season points-to-date (`season_stats_source`) is descriptive only, and must stay that way.** It is the one live source that reads REALIZED results on the in-season path. It is attached to recommendations (`gameplan.PlayerMetrics.season_ptd`) and written into the weekly log, and nothing reads it back into a valuation, ranking, or the optimizer. Folding it into the pricing would be a scoring change no backtest in [docs/dev/BACKTEST.md](docs/dev/BACKTEST.md) has graded, and it would double-count — a live `ros_board` is built from projections that already price in past production. `tests/test_gameplan.py::TestSeasonPointsToDateIsDescriptiveOnly` proves it by building the same plan twice; `tests/test_projections_actuals.py::TestSeasonToDateNeverReachesTheBacktest` proves `ffbot/history/` and `ffbot/backtest/` can't reach the fetch at all, since it is by definition the results-bearing source `as_of()` promises never to touch.
- **The draft table's pick confidence (`p_best`) is presentational only.** `edge.best_pick_probabilities` is a monotone transform of `value`, so it can only restate the ranking, never change it — `ffbot/draft.py` must never reference it (asserted structurally in `tests/test_edge.py`). Its temperature (`DraftConfig.pick_confidence_scale`) must stay an ABSOLUTE scale in season points: deriving it from the displayed rows' own spread (e.g. `edge.decision_scale`) would make every pick render the same shape and destroy the standout-vs-toss-up distinction the column exists for. `tests/test_edge.py::TestPickConfidence::test_scale_is_absolute_not_relative` is the guard.
- **A recommendation's metrics must be carried as typed fields, not re-parsed from its `reason` text.** `week.WaiverCandidate`'s typed `net` components were added for exactly this and then went unread for a while; `gameplan.PlayerMetrics`/`DecisionMetrics` are their consumer. New numbers behind a recommendation belong on those dataclasses and in `webapi`'s serializers — which `ffbot/week_log.py` reuses rather than copying, the same anti-drift rule `draft_report.py` follows for `rec_row`.
- **League demand is DESCRIPTIVE, and a speculative row is not a move.** `ffbot/demand.py` reads what other managers actually did — rivals' failed waiver claims (already fetched every run and, until 2026-09-16, discarded twice), Sleeper's global `trending` adds, and the week-over-week ownership delta. It reaches `week.SpeculativeCandidate.demand` and `gameplan.PlayerMetrics.demand` and nothing else: no `net`, `value`, `gain`, `urgency` or `denial.denial_value` reads it (`tests/test_gameplan.py::TestWaiverDemandIsDescriptiveOnly` builds the same plan twice and diffs). Beyond "no backtest has graded it" there is a permanent reason — those endpoints publish only a current reading and keep no archive, so a valuation version could only ever be graded FORWARD (BACKTEST.md's B16). `DemandSignal.is_retrospective` carries the timing split in the TYPE: a rival's claim does not exist in Sleeper's log until the run has processed it, so it is a Wednesday retrospective and the Tuesday check filters on that field, never on the source name. `GamePlan.speculative` follows `ir_stash`: its rows carry no `net`, never enter `post_roster`, never consume a droppable key or an open spot, never count against `recommend_count`, and never trigger a notification — they ride along on a message already being sent. A row must also be genuinely BELOW the drop it would cost on some horizon (`week._is_below_your_worst`); a backup at a filled position also scores `gain <= 0`, and the first live run put two of them above the case the section exists for.
- **A candidate the waiver scan discards must leave a record.** `week.waiver_candidates` had two silent exits — the `waiver_pool_size` VOR truncation and the `gain <= 0.0` filter — while the noise floor four lines below the latter carefully recorded its own refusals under "'nothing worth recommending' and 'nothing priced' must not look the same." `week.ScanTrace` is the out-parameter that closes it (`None` is bit-identical to not passing one), and `trace.scanned == priced + zero_gain + len(noise_floored)` is asserted structurally. The `gain <= 0` bar itself STAYS: `week_gain` is exactly 0.0 for anyone who doesn't crack the starting lineup and `ros_gain` is strictly negative at a position with a hole, so a bench-quality add is `<= 0` by construction, not by mispricing. The fix is the record, not the removal.
- **A dial that is set but has no input must say so.** `report._INTEL_BACKED_DIALS` pairs each weight with the researched `WeeklyPlayerIntel` field it reads, and `_intel_coverage_alerts` surfaces both zero coverage and PARTIAL coverage — the latter matters more, because `week.usage_score(None)` returns 0.0 rather than a neutral 0.5, so which players are covered is itself a ranking effect. `tests/test_intel_coverage.py` derives the field set from `week._parse_player_entry`'s own `_score_field` calls and requires every one to be a registered dial input or explicitly declared not one, so a new dial cannot go inert unnoticed. This exists because `usage_weight`, `momentum_weight`, `divergence_weight`, `volatility_weight` and `upside_lean_weight` shipped set, sliderized, and structurally inert for an entire season: nothing ever wrote the fields they read, and `_momentum_multiplier` returned exactly 1.0 for every player, every run, with nothing saying so. Whether to wire or retire them is W8.
- **The push IS the product; the GUI is secondary.** The manager reads ntfy notifications and rarely opens `scripts/gui.py` (his call, 2026-09-16). Since Sleeper has no write endpoint, every recommendation is executed by hand — so the moment of decision is wherever he is when the notification lands, not at a desk. A change that surfaces only in the GUI, or only in `week_report.py`'s terminal output, has not reached the decision. Note that `plan.notes` and `_all_alerts` reach the CLI and the GUI but NEVER a push, so a diagnostic added there is invisible by default: decide deliberately whether it belongs in the body. The body is built in `scripts/autorun.py` (`actionable_summary`, `waiver_summary`, `post_waiver_summary`, the `*_heartbeat` pair) — `ffbot/notify.py` is pure transport and formats nothing. The two standing guards hold: `actionable_summary` decides whether to WAKE someone and stays conservative (a speculative row may ride along on a message already going out, never trigger one), and a quiet check must still say something, because the ABSENCE of a message has to remain the failure signal. Phone space is the real constraint — prefer fewer, better-ordered lines over completeness.
- **A Validated dial must have a wire, and the wire must be one implementation.** `usage_weight`, `momentum_weight`, `divergence_weight`, `volatility_weight` and `upside_lean_weight` are classed **Validated** in [docs/dev/SPICE.md](docs/dev/SPICE.md) and were structurally inert in production for a whole season — the fields they read were only ever written by a hand-typed `weekly/week-NN.yml` entry. `ffbot/live/form.py` is the wire (`form_source: sleeper`), computing them from the league's own realized weekly stats; research still wins field by field (`report._merge_form_scores`, the `_merge_kalshi_scores` rule). The MATH lives in `ffbot/form.py` and is shared with `ffbot/history/signals.py` rather than reimplemented: the shipped weights were selected against one definition of these signals, so a live path computing a slightly different one would be running an untested configuration while claiming a validated one. Three completed games are required (`form.MIN_GAMES`), so all five are silent through week 3 of a season and speak from week 4 — by design, and the coverage alert says so rather than leaving it to be rediscovered. Ties in `percentile_rank_within_position` SHARE the average rank: with `min_games == recent_games == 3` every week-4 trend is identically 1.0, and spreading that across 0–100 by dict order manufactured a ranking out of no information in exactly the first week these dials ever spoke.
- **A `SignalProvider` (`ffbot/history/signals.py`) must never be folded into `as_of()` itself.** `as_of()`'s leakage guarantee is that it never fetches a results-bearing source at all — a provider that needs `stats_player_week` (even read leakage-safely, strictly before the target week) stays outside that boundary and merges in afterward via `WeekSnapshot.with_signals()`. Don't "simplify" this by moving a provider's fetch inside `as_of()`; that's exactly the exception the guarantee exists to never need.
