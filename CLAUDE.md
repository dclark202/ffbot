# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ffbot` is a local web GUI (`scripts/gui.py`, port 8321) live-synced to one Sleeper fantasy football league: a draft room with live pick sync, and a read-only weekly manager that auto-loads the current week's real roster/lineup/waiver state. Terminal CLIs (`scripts/draft.py`, `scripts/week_report.py`) share the identical engine, draft log, and lineup state as fallbacks — see [docs/REFERENCE.md](docs/REFERENCE.md) for those and the full config reference; [docs/GUIDE.md](docs/GUIDE.md) is the day-to-day GUI walkthrough. Everything is read-only against Sleeper's public, unauthenticated API — permanently advisory, since Sleeper has no write endpoint at all. The shipped `config.yml` is live-by-default (`projection_source`/`roster_source`/`standings_source`/`league_rosters_source`/`board_points_source` all set to `sleeper`); the code-level dataclass defaults in `ffbot/config.py` are offline, used only when a key is deleted entirely.

## Architecture

- **`ffbot/sleeper/`** — the read-only, unauthenticated HTTP client for Sleeper's public API (`SleeperClient`, stdlib `urllib` only). Documented endpoints (state, user, leagues, rosters, users, matchups, drafts, players, trending) are stable; two undocumented ones (season projections/ADP, ownership%) are unsupported by Sleeper and every caller must treat a fetch failure as "no data this run." Per-endpoint TTL cache (`cache.py`); `draft()`/`draft_picks()` are never cached (a live draft poll needs real-time reads). `models.py` translates Sleeper's word-based injury status onto this repo's existing single-letter vocabulary.
- **`ffbot/live/` + `ffbot/markets/`** — two more no-auth live clients feeding the weekly outside-data signals: `live/schedule.py` (real NFL schedule, always refetched), `live/weather.py` (Open-Meteo forecast), `live/conditions.py` (merges both plus Kalshi odds, then layers a human's hand-typed `weekly/week-NN.yml` research UNDER the auto-fetched numbers — a hand-typed value always wins). `markets/kalshi.py`/`kalshi_nfl.py` are the raw and NFL-semantic Kalshi clients (game odds are always live; per-player prop markets are gated on `use_untested_features`). Every fetch here degrades independently with a surfaced alert, never a crash.
- **Core engine** — `ffbot/models.py` (the `Player` shape and status/slot vocabulary, tracing back to this project's original Yahoo target but unchanged since Sleeper translates onto it at the boundary), `ffbot/lineup.py` (the deterministic, exactly-optimal bipartite-matching lineup optimizer — see the design invariant below), and `ffbot/policy.py` (drop guardrails: undroppable flags, ownership/draft-round protection, temporary-unavailability refusal).
- **Weekly path** — `ffbot/week.py` (status overrides, weather/Vegas/venue adjustments, the volatility/upside-lean variance pair), `ffbot/gameplan.py` (the unified weekly recommendations engine behind both the GUI and `week_report.py --waivers` — one pool, one coherent plan, streaming/denial folded in as reasons not categories), `ffbot/denial.py` (tactical denial, threat scored by playoff-bubble seed distance — and, via its fungibility-discounted `denial_value`, the "claim now vs. wait for free agency" term on both waiver and stream rows), `ffbot/roster_source.py` (roster.yml parsing + lineup-state persistence), `ffbot/sleeper_roster.py` (the live-Sleeper roster route), `ffbot/report.py` (`load_everything`, the shared loader with one alert list per live seam), `ffbot/webapi.py` (GUI JSON serializers), `ffbot/week_log.py` (the per-run JSON recommendation record — the weekly analog of `ffbot/draft_report.py`), and `ffbot/notify.py` (the one OUTBOUND live seam — push notifications for `scripts/autorun.py`).
- **Draft path** — `ffbot/board.py` (frozen pre-draft board: FantasyPros CSV loading with graceful missing-file handling, derived replacement level, VOR/tiers, the live Sleeper points overlay applied strictly after league scoring), `ffbot/draft.py` (pick math, ADP survival, `DraftState`), `ffbot/edge.py` (contrarian valuation terms, every weight a fraction of the per-pick decision scale), `ffbot/draft_ui.py` (pure state machine shared by the terminal and GUI), `ffbot/draft_sync.py` (live Sleeper pick sync, main-thread-only `DraftState` mutation), `ffbot/names.py` (two deliberately separate matchers: strict pre-draft ID reconciliation vs. permissive live search), and `ffbot/intel.py` (researched `draft/intel.yml`).
- **`ffbot/history/` + `ffbot/backtest/`** — point-in-time replay against real NFL seasons, for validating tuning/edge weights against outcomes instead of judgment alone. `history.index.as_of()` is the single point-in-time boundary (never fetches a results-bearing source); `backtest/` may read realized outcomes only through `history.actuals.week_actuals`. See [docs/dev/BACKTEST.md](docs/dev/BACKTEST.md) for the full design and [docs/dev/SPICE.md](docs/dev/SPICE.md) for the evidence behind each dial's shipped value.
- **`ffbot/training.py` + `ffbot/training_export.py`** — synthetic draft situations (frozen `webapi.draft_state_json()` snapshots from mock drafts with bots in every seat) exported as a standalone HTML page a human reviewer opens with no server, for a second, high-volume source of judgment on recommendations. Grading reuses `ffbot/draft_report.py`'s `taken_block` so a training verdict and a real draft-report entry are never two different shapes for the same thing. See [docs/dev/TRAINING.md](docs/dev/TRAINING.md) for the tool and [docs/dev/TRAINING-FINDINGS.md](docs/dev/TRAINING-FINDINGS.md) for what it has actually found (its in-season twin is [docs/dev/INSEASON-FINDINGS.md](docs/dev/INSEASON-FINDINGS.md)) and the backtest cells that are queued behind it; every finding it surfaces is a hypothesis, not a change, until `scripts/backtest_draft.py` agrees.
- **`scripts/` + `web/`** — thin shells around the packages above. `scripts/gui.py` is single-threaded on purpose (one shared, mutable `UiState`, no lock). `scripts/schedule_autorun.py` wraps Windows Task Scheduler (or prints the `cron` equivalent) to run `scripts/autorun.py` on a recurring interval. `web/draft_render.js` holds the recommendation-table/roster/opponents rendering shared between the live draft room (`web/draft.html`) and the offline training-pack reviewer (`web/train.html`).

Module docstrings carry the detail this section used to — read the file itself for exactly how a given piece works.

## Design invariants worth preserving

- **Config, not code, for tuning.** New thresholds/weights belong in `config.yml` + the corresponding dataclass in `ffbot/config.py`, not hardcoded.
- **The optimizer must stay exact and deterministic.** Any change to `ffbot/lineup.py` should preserve: (1) exact optimality (not a heuristic), (2) stable output across runs (ties break on player name), (3) the flex-seating rule, and (4) minimal-move preference among assignments the seating rule cannot separate. Both the in-season path and the draft assistant depend on this.
- **Seating is a decision, not a formality, and the seating rule outranks minimal-move.** Every perfect matching of the chosen starters scores identically, so points cannot choose between them — but a flex is the only slot accepting more than one position, and a platform locks each player at his own kickoff, so *which* identically-scoring matching you return is a real choice. `lineup._flex_seating_order` makes it: an early-kickoff player is kept out of the flex first (parking him there locks the roster's only versatile slot for the whole week), then the flex goes to the most replaceable starter. Minimal-move was ORIGINALLY the only preference here, and that is exactly why the bug existed: a roster imported from Sleeper arrives pre-seated, so a minimal-move-only pass ratifies whatever was already there and reports no moves — silently endorsing your best player sitting in the flex. Minimal-move survives as the third component of the sort key and via slots comparing by NAME (a shift between two WR slots is not a move). Don't re-promote it above the rule. A move between two starting slots is labelled "no points change" rather than a projection, so a zero-point reseat never reads as churn.
- **Drops are the one in-season action guarded by explicit policy**, not a confirmation step, because the agent is meant to act unattended. New irreversible actions should get the same treatment: a `Verdict`-returning policy function with the reason surfaced, not a silent allow/deny.
- **`scripts/draft.py`, `scripts/week_report.py`, and `scripts/gui.py` must stay importable and runnable with no network at module level.** `ffbot.sleeper`/`ffbot.sleeper_roster`/`ffbot.projections.sleeper` are all imported lazily, inside the function that actually needs them (`_build_sync`, `report.load_everything`'s live branches, `board.load_board_from_config`'s overlay branch) — the offline paths must keep working with no network at all, not just "no credentials." `week_report.py`'s own research step (weather/injuries/Vegas) is deliberately kept *outside* the script entirely, in the `/gameday` command — see `ffbot/week.py`'s module docstring.
- **Every live network call takes an injectable `opener`/client, and every fetch failure degrades gracefully with a surfaced alert — never a silent success and never a crash.** This is the same contract across every live seam in the repo: `ProjectionSourceConfig`'s `"sleeper"`, `RosterSourceConfig`'s `"sleeper"`, `DraftConfig.board_points_source`'s `"sleeper"`, and `ffbot.draft_sync.DraftSync`'s poll loop. A test asserting this must exist for any new live seam, matching `tests/test_history_index.py::TestAsOfLeakageGuarantee`'s pattern of proving it structurally, not just by inspection.
- **Pre-draft ID matching vs. live TUI search are different problems** (see `ffbot/names.py` above) — don't collapse them into one matcher.
- **Season-long valuation always passes `week=None`** to `optimize()` — `draft.need()` is always a season-long decision. `week.waiver_candidates()`/`rank_streamers()` now accept an optional real `week` too, but only to zero/exclude a candidate's *this-week* contribution when they're on bye that week — the rest-of-season side of any blend stays on the season board (or `ros_board`, when live) and must never be zeroed by it. Weekly *lineup* decisions (`week.build_week_brief`) are the one place a real week number was always correct and required.
- **A `Board`'s `points` overlay (`_apply_points_overlay`/`rescale_board_points` in `ffbot/board.py`) must run AFTER `apply_league_scoring`, never folded into the CSV/row merge ahead of it.** A merged-in `stats` field from an untouched source silently lets `apply_league_scoring`'s recompute clobber the overlay's live number right back to the frozen data it was meant to replace — a real bug this repo shipped and caught once already (see `ffbot/board.py`'s docstring on `_apply_points_overlay` and its regression test in `tests/test_board.py`).
- **`scripts/gui.py` is single-threaded on purpose.** The draft session is one shared, mutable `UiState` with no lock — serializing every HTTP request through one thread (`http.server.HTTPServer`, not `ThreadingHTTPServer`) is what keeps `DraftState` main-thread-only (see `ffbot/draft_sync.py`'s existing invariant on this) without adding one. Don't switch it to a threading server without adding real synchronization.
- **`use_untested_features` gates FEATURES, never intensity, and the gate runs LAST.** `SEASON_UNTESTED_DIALS`/`DRAFT_UNTESTED_DIALS` are exactly `{k : level-3 value == 0 and level-4 value != 0}` — the dials level 4 switched on from nothing, not the ones it merely turned up. `tests/test_config.py::TestBaselineAndUntestedToggle` derives that set from the presets and asserts the match, so the pair cannot drift. In `_resolve_block`, the gate applies AFTER explicit per-key overrides: an unticked box forces those dials to exactly 0.0 even when the overlay carries a slider value, which is what makes the checkbox authoritative rather than advisory. Don't "simplify" it by applying the gate before the overrides, and don't fold an evidence-backed dial into the untested set to make a level-4 preset reproducible in one click — that's a slider's job.
- **A waiver claim's cost is ABSOLUTE, never a fraction of the gain it buys.** `week.priority_option_cost` prices a rolling-priority slot from the slot and `week.decision_scale`, and `week.claim_verdict`'s contract is that `claim_cost` does not depend on `gain`. The original form was `priority_value * gain * (1 - p/num_teams)`, which made `claim_cost < gain` algebraically equivalent to a gain-independent predicate — so `HOLD PRIORITY` was unreachable dead code and a +0.6-point DEF sidegrade was typed a CLAIM exactly as readily as a +54-point starting RB. It shipped, and it pushed that +0.6 row to a phone. `tests/test_week.py::TestClaimVerdictEconomics` asserts gain-invariance and reachability structurally, reading `priority_value` from `SEASON_BASELINE` rather than hardcoding it. A HOLD verdict must also be charged NOTHING, or `gameplan`'s `net <= 0` bars delete the row instead of demoting it to an ordinary add — "not worth a claim" must never silently become "not worth mentioning."
- **No displayed recommendation number is the ros/week blend.** `value`/`net` are `ros_blend * (a rest-of-season TOTAL) + (1 - ros_blend) * (ONE week's points)` — an average of two scales differing by ~17x, which denominates nothing. It is the internal ranking key and is labelled `rank key … (blend)`; everything shown to a human is points per week (`DecisionMetrics.week_gain` and `ros_gain_per_week`, rendered by `week_report._per_week_strip`). Presenting the blend as points is how a move worth +0.2 points read as "+0.6" and got notified. New numbers behind a recommendation go on `DecisionMetrics` in a stated unit.
- **A streaming position's gain is weighted less on rest-of-season value, but never zero** (`SeasonConfig.stream_ros_blend`, 0.25 against `ros_blend`'s 0.5). Rest-of-season value is something you ACQUIRE and at a streamed position you never do — the counterfactual is "whatever DEF is best next week", not "no DEF". But 0.0 was tried and INVERTS the board: it ranked a tier-4 defense (rest-of-season −2.0/wk) above a tier-3 one for a +1.2-point weekly matchup edge. You still have to hold whoever you pick up, and the tool recommends one move, not a season of churn.
- **`config.yml` is never rewritten by code.** It's hand-narrated with comments a YAML round-trip would destroy. Anything that needs to *write* settings (the GUI's Settings page) writes to the gitignored `config.local.yml` overlay instead (`_deep_merge`d on top at load time) — never add a code path that calls `yaml.safe_dump` against `config.yml` itself.
- **Historical replay must go through `ffbot.history.index.as_of()`.** No backtest code may read a historical data file (`data/history/*.csv`) directly — `as_of()` is the single point-in-time boundary, and its leakage guarantee (never fetching a results-bearing source) only holds if every caller actually goes through it. See [docs/dev/BACKTEST.md](docs/dev/BACKTEST.md)'s leakage register.
- **A rank→points (or any) calibration used for historical projections must be fit on seasons other than the one being graded.** `ffbot.history.projections.ecr_projections` enforces this by raising, not just documenting it — fitting on the test season is the single most likely way to fake a good backtest result.
- **`ffbot/backtest/` may read realized outcomes only through `ffbot.history.actuals.week_actuals`, never `WeekSnapshot.game_rows` directly.** `game_rows` is `ffbot.history.index`'s own separate post-hoc-scoring channel; routing every grading read through one function keeps "did a decision accidentally see the answer" a one-place-to-check question.
- **Season points-to-date (`season_stats_source`) is descriptive only, and must stay that way.** It is the one live source that reads REALIZED results on the in-season path. It is attached to recommendations (`gameplan.PlayerMetrics.season_ptd`) and written into the weekly log, and nothing reads it back into a valuation, ranking, or the optimizer. Folding it into the pricing would be a scoring change no backtest in [docs/dev/BACKTEST.md](docs/dev/BACKTEST.md) has graded, and it would double-count — a live `ros_board` is built from projections that already price in past production. `tests/test_gameplan.py::TestSeasonPointsToDateIsDescriptiveOnly` proves it by building the same plan twice; `tests/test_projections_actuals.py::TestSeasonToDateNeverReachesTheBacktest` proves `ffbot/history/` and `ffbot/backtest/` can't reach the fetch at all, since it is by definition the results-bearing source `as_of()` promises never to touch.
- **The draft table's pick confidence (`p_best`) is presentational only.** `edge.best_pick_probabilities` is a monotone transform of `value`, so it can only restate the ranking, never change it — `ffbot/draft.py` must never reference it (asserted structurally in `tests/test_edge.py`). Its temperature (`DraftConfig.pick_confidence_scale`) must stay an ABSOLUTE scale in season points: deriving it from the displayed rows' own spread (e.g. `edge.decision_scale`) would make every pick render the same shape and destroy the standout-vs-toss-up distinction the column exists for. `tests/test_edge.py::TestPickConfidence::test_scale_is_absolute_not_relative` is the guard.
- **A recommendation's metrics must be carried as typed fields, not re-parsed from its `reason` text.** `week.WaiverCandidate`'s typed `net` components were added for exactly this and then went unread for a while; `gameplan.PlayerMetrics`/`DecisionMetrics` are their consumer. New numbers behind a recommendation belong on those dataclasses and in `webapi`'s serializers — which `ffbot/week_log.py` reuses rather than copying, the same anti-drift rule `draft_report.py` follows for `rec_row`.
- **A `SignalProvider` (`ffbot/history/signals.py`) must never be folded into `as_of()` itself.** `as_of()`'s leakage guarantee is that it never fetches a results-bearing source at all — a provider that needs `stats_player_week` (even read leakage-safely, strictly before the target week) stays outside that boundary and merges in afterward via `WeekSnapshot.with_signals()`. Don't "simplify" this by moving a provider's fetch inside `as_of()`; that's exactly the exception the guarantee exists to never need.
