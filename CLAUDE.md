# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ffbot` is two tools around one Yahoo fantasy football team, plus a web GUI on top of both:

1. **In-season manager** — the weekly start/sit + waivers + streaming brief (`scripts/week_report.py`, driven by the `/gameday` command), built on the same optimizer as the draft assistant. A manual `roster.yml` baseline works today with no Yahoo access; a live Yahoo-fetch route and, eventually, unattended writes via GitHub Actions are the natural extension once API access lands — see [docs/INSEASON.md](docs/INSEASON.md) for the full design and milestones.
2. **Live snake-draft assistant** — a keyboard-driven, fully offline TUI (`scripts/draft.py`) that recommends picks in real time using the same optimizer as the in-season manager.
3. **Web GUI** (`scripts/gui.py`, `ffbot/webapi.py`, `web/`) — a local, dependency-free `http.server` front end exposing both of the above as browser pages, sharing the identical compute layer and the identical `draft_log.jsonl`/lineup-state files as the two CLIs.

## Commands

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt   # Windows; .venv/bin/pip on macOS/Linux

pytest                                            # run the full suite
pytest tests/test_lineup.py                       # one file
pytest tests/test_lineup.py::test_name -v          # one test

.venv/Scripts/python scripts/authorize.py          # one-time Yahoo OAuth (never in CI)
.venv/Scripts/python scripts/whoami.py              # verify the connection end-to-end

.venv/Scripts/python scripts/draft.py --slot 4                       # run the live draft assistant
.venv/Scripts/python scripts/draft_export.py --board rankings.csv    # pre-draft board -> Yahoo custom-rankings export
.venv/Scripts/python scripts/gui.py --slot 4                         # web GUI, http://127.0.0.1:8321/

.venv/Scripts/python scripts/week_report.py --week 3 --stream K DEF --waivers --faab 45   # weekly brief (see docs/INSEASON.md)
```

No lint/format tooling is configured in this repo.

## Architecture

### In-season path

`scripts/whoami.py` uses `ffbot.auth.YahooSession` to talk to `yahoo_fantasy_api`, discovers `league_id` / `team_key` / `roster_positions`, which get pasted into `config.yml`. `scripts/week_report.py` is the weekly runner: it works today from a hand-maintained `roster.yml` (no Yahoo access needed), and is built so a live Yahoo fetch can replace that one input without touching anything downstream. See [docs/INSEASON.md](docs/INSEASON.md) for the full design, the three roster-source routes, and the M1→M4 milestone plan.

- **`ffbot/auth.py`** — Hand-rolled Yahoo OAuth2, not `yahoo_oauth`. `yahoo_oauth` assumes a token file on disk, which doesn't fit CI where the refresh token lives in a GitHub Actions secret and rotation has to be written back out. `YahooSession` implements the exact four members `yahoo_fantasy_api.yhandler.YHandler` touches (`.session`, `.access_token`, `.refresh_access_token()`, `.oauth.get_session()`) so it can be handed to `yahoo_fantasy_api.Game` as `sc`. Yahoo may rotate the refresh token on any refresh; persistence via the `on_refresh` callback (`env_file_persister` locally, `github_secret_persister` in CI) runs *before* anything else in `refresh_access_token`, so a crash later in a run can never strand a rotated token and lock the agent out mid-season.
- **`ffbot/config.py`** — All tunable behavior (scoring weights, drop protections, FAAB limits, draft valuation, weekly spice) loads from `config.yml` via nested dataclasses (`ScoringConfig`, `DropPolicyConfig`, `FaabConfig`, `DraftConfig`, `SeasonConfig`). The intent is that tuning strategy is a config edit, never a code change. `Config.roster_positions` also seeds the draft assistant's slot layout before a real Yahoo connection exists. `SeasonConfig`'s primary dial is `spice_level` (1-5, resolved by `SeasonConfig.from_spice_level` into five underlying weights) rather than the raw weights themselves — weather/Vegas alone mostly agree with consensus on a calm week, so a single named level is what keeps "how contrarian" legible without hand-tuning five numbers, and any one field can still be overridden individually on top of the preset. `Config.load` additionally merges an optional sibling `config.local.yml` on top (deep-merged; see `_deep_merge`) — the GUI's Settings page writes there instead of `config.yml`, whose comments a YAML round-trip would destroy. `DraftConfig.order` (`"snake"`/`"linear"`) and `LeagueScoring.my_opponent`/`SeasonConfig.denial_opponent_boost`/`denial_seed_window` are newer additions, all documented in [docs/SETUP.md](docs/SETUP.md)'s configuration reference.
- **`ffbot/models.py`** — `Player` fields deliberately mirror the keys `yahoo_fantasy_api.Team.roster()` returns, so the fetch layer is a rename-free translation. `SLOT_ELIGIBILITY` encodes Yahoo's slot-naming scheme (`"W/R/T"` = flex accepting WR/RB/TE). `STATUS_OUT` / `STATUS_QUESTIONABLE` classify Yahoo's injury codes into hard-bench vs. discount-but-start. `team` exists for the same reason — Yahoo's roster payload carries it, and the weekly weather/Vegas signals need it to look up a player's game.
- **`ffbot/lineup.py`** — Deterministic, offline optimizer (no LLM — it must be fast and predictable for a Sunday-morning deadline, and fast enough to call thousands of times during a live draft, see below). Modeled as bipartite matching: startable players form a transversal matroid, so taking players in descending projected-score order and greedily augmenting (Kuhn's algorithm, `_augment`) yields the exactly optimal lineup, not just a good one. A second matching pass then picks *among* equally-optimal assignments the one requiring the fewest actual position changes, so the optimizer doesn't churn equivalent slots for zero score gain — every unnecessary move is a Yahoo write and noise in the audit log. This module is the shared core both the in-season path and the draft assistant build valuation on top of. Note that `optimize()` never mutates a `Player`'s `selected_position` to reflect where it just placed them — the new slot exists only as the first element of each `assignments` tuple, since `optimize()` is a pure function and writing the change is the caller's job; `week.py`'s lineup-state persistence exists specifically to bridge that gap across runs.
- **`ffbot/policy.py`** — Guardrails specifically on *drops*, since lineup changes are freely reversible but a drop is not (another manager can claim the player instantly). Every rule is phrased as "would I regret this Monday?": undroppable flags, a `never_drop` list, early-draft-round protection, high-ownership protection, and a refusal to drop anyone only *temporarily* unavailable (bye week, Questionable). FAAB bid sizing (`max_faab_bid`) is similarly capped by both a percentage of remaining budget and a hard reserve floor. `policy.droppable()` sorts by `percent_owned`, which is real signal once Yahoo is live but is `None` for every player under the manual `roster.yml` route — callers on that route must pre-filter to a sensible candidate pool (e.g. the optimizer's own bench) before calling it, not hand it the full roster; see the comment in `week.waiver_candidates` for the bug this caused when that wasn't done (it suggested dropping a starting QB).
- **`ffbot/week.py`** — The in-season analog of `ffbot/edge.py`: status overrides, weather (`data/stadiums.yml` for the dome gate; wind/precip discount pass-heavy positions, RB gets partial relief, DEF is untouched since bad weather tends to help defenses), a venue-disruption discount for neutral-site/international games (`GameInfo.venue` overrides the usual home/away stadium lookup; `international` gates the off-by-default `venue_disruption_weight`), Vegas implied-total tilt (inverted for DEF — the opponent's total is what matters, not the team's own), and a `volatility_weight`/`upside_lean_weight` spice pair that exists specifically so a close start/sit call can still go to the higher-ceiling player on a calm week with no weather/Vegas story — without it the system would mostly just re-derive consensus. All weights are fractions of `decision_scale` (the point spread across the roster), same reasoning as `edge.decision_scale`. `waiver_candidates` reuses `draft.need()`'s marginal-lineup-value trick against a *season-scale* roster (via `_season_scale_roster`, matched onto the existing draft board) — comparing it against weekly-scale numbers directly is a unit error that makes every waiver candidate look like a massive upgrade; it also takes an optional `week` to zero a bye-week candidate's this-week contribution (`rank_streamers` excludes them outright — a streamer who can't play isn't a candidate at all). DEF team identity is resolved through `names.defense_key` before any lookup (`_resolve_team`), because board defenses routinely carry a blank or full-city-name `team` field rather than a clean abbreviation, and weather/Vegas/games data is keyed by abbreviation.
- **`ffbot/denial.py`** — Tactical denial: `threat()` scores a rival 0..1 by playoff-bubble seed distance, plus two additive, individually no-op boosts — `opponent_boost` when the rival is `league.yml`'s `my_opponent` this week, and a `seed_window` proximity boost (gated by `is_playoff_push`, the final few weeks of `regular_season_weeks`) for a rival near your own seed. Needs `league_rosters.yml` (rival rosters) and `league.yml`'s `teams:` standings; either missing collapses every function here to an exact no-op.
- **`ffbot/roster_source.py`** — Turns `roster.yml` (bare names — no slots; the optimizer decides those fresh every run) into `Player`s, matched against weekly FantasyPros projections when available and the existing season-long draft board (rescaled to a per-week baseline) otherwise, so the report runs every week without requiring a fresh download each time. A roster name that matches nothing is always surfaced, never silently dropped — the dangerous failure mode is a real rostered player quietly vanishing from every recommendation. Also owns lineup-state persistence (`load_lineup_state`/`save_lineup_state`/`apply_lineup_state`) — see the `lineup.py` note above for why this exists.
- **`ffbot/report.py`** — `load_everything(...)`: the shared loader behind both `scripts/week_report.py` and the GUI's weekly endpoint (config, weekly intel, board, matched roster). Raises `ReportError` (never `SystemExit`) so the GUI can catch it; `scripts/week_report.py`'s own `load_everything(args)` is a thin wrapper that turns `ReportError` back into the `SystemExit` the CLI has always used.
- **`ffbot/webapi.py`** — JSON serializers for the GUI: `draft_state_json` mirrors every section of `draft_ui.render()`; `weekly_report_json` mirrors `week_report.py`'s `main()`, including the same section-gating (no board → no roster status, etc.) and the same "commit the lineup or don't" choice (`commit_lineup=False` is a what-if run, same contract as `--no-save-state`).
- **`ffbot/roster_editor.py` / `ffbot/weekly_editor.py`** — Read/write helpers for the GUI's roster and weekly-intel editors. `weekly_editor` is deliberately matchup-centric (one row per game, not per team) even though `week.WeeklyIntel.games` stores each game twice, mirrored — editing the raw per-team shape invites the two sides drifting apart (wind entered on one team's row, not the other); the editor writes both mirrored sides from a single row so that can't happen.
- **`ffbot/draft_store.py`** — File-backed archive/save/load for the draft log, used by both `scripts/draft.py`'s local `reset`/`save`/`load` commands and the GUI's equivalent buttons. Pure I/O, deliberately outside `draft_ui.handle()` (which stays a pure state machine).
- **`ffbot/intel.py`** — Loads `draft/intel.yml`, pre-draft only. `ffbot/week.py` has its own parallel loader (`load_weekly_intel`/`WeeklyIntel`/`WeeklyPlayerIntel`) for `weekly/week-NN.yml` rather than reusing this module directly — the two files carry different shapes (the weekly one also has a `games:` section for kickoff time/weather/Vegas/venue that has no draft-time analog) — but both are held to the identical factual/speculative contract (see [docs/DRAFT.md](docs/DRAFT.md) and [docs/INSEASON.md](docs/INSEASON.md)) and both use the same unmatched-name philosophy: `names.normalize_name` matching, a fuzzy suggestion on a miss, never a silent crash or a silently dropped player, and a missing file leaves the board/roster bit-identical.

### Draft assistant path

`scripts/draft.py` is a thin keyboard/render shell around a pure state machine, so the interaction loop needs no pty to test. Everything runs offline against a pre-built board; Yahoo sync is optional and lowest-priority.

- **`ffbot/board.py`** — Loads and values the frozen pre-draft board from FantasyPros CSV exports (`read_fantasypros` sniffs headers across their rankings/ADP/projections products; `_merge_csv_rows` combines multiple exports by normalized name+position). Replacement level is *derived*, not assumed: it scales the league's starting slots by `num_teams` and runs `lineup.optimize()` over the whole player pool — the matroid-exchange property means truncating each position to its top `S_p` candidates first is exact, not approximate, and makes the call ~8x cheaper. VOR (value over replacement) and tiers (gap-based, normalized by each position's median gap so it's scale-free across QB vs. K) are computed once and frozen for the draft.
- **`ffbot/draft.py`** — Live pick math: snake order (`pick_number`/`round_and_slot`, both order-aware — `order="snake"` reverses direction each round, `"linear"` doesn't), ADP survival probability (`Normal(adp, sigma)`, conditioned on already surviving to the current pick), and `DraftState` (the pick log + roster + `order`). Valuation (`need`/`value`) is built on `lineup.optimize()` rather than hand-tuned positional weights: `need` is the marginal season-long optimal-lineup points gained by drafting a candidate vs. a replacement-level player at that position, given the roster so far; `value` adds a depth term (clamped VOR) so late-round players aren't all valued at zero once starters are full. `recommend()` scans the *entire* remaining pool every pick (cheap enough — tens of ms against 500+ players) rather than shortlisting. `alerts()` flags positional runs, tier cliffs, bye-week collisions (via the same optimizer, comparing against a week=`None` baseline so it stays quiet early when the roster is mostly empty), and survival-based "room" warnings.
- **`ffbot/edge.py`** — Contrarian valuation terms layered on `draft.need`: round-ramped risk appetite (`risk_ramp` — floor early, ceiling late), volatility from cross-site ADP disagreement (`adp_spread`, ranked within position), QB↔pass-catcher stacking, ADP arbitrage, and a deficit-urgency roster-balance term. Every weight defaults to 0.0 (exact no-op; the aggressive values live in `config.yml`), weights are *fractions of the per-pick decision scale* (never absolute points — round-1 gaps are 100+ points, round-12 gaps are 2-3), and K/DEF are excluded from every term (`EDGE_EXCLUDED_POSITIONS` — each term misreads them; the comment there explains why per-term). `recommend()` additionally enforces `position_caps` (hard), defers K/DEF until the last two rounds, and force-fills empty dedicated starting slots when picks run out.
- **`ffbot/intel.py`** — Loads researched player intel from `draft/intel.yml` (produced by Claude Code web research pre-draft — see [docs/DRAFT.md](docs/DRAFT.md) for the cadence). Matched by `names.normalize_name`; unmatched entries warn with a fuzzy suggestion, never crash; a missing file leaves the board bit-identical. `upside` feeds the value function via `upside_weight`; `note` lands verbatim in the recommendation WHY column, so notes are written as short plain English.
- **`ffbot/draft_ui.py`** — Pure `handle(state, line) -> UiState` / `render(state) -> str`, no terminal dependency; both `scripts/draft.py`'s terminal loop and `scripts/gui.py`'s HTTP handler call the same `handle()`. `reset`/`save <name>`/`load <name>` are intercepted *before* `handle()` (see `scripts/draft.py`'s `handle_local_command`), since they touch the filesystem (`ffbot/draft_store.py`) and `handle()` must stay pure. Every typed command is appended to a resumable log (`draft_log.jsonl`); a GUI row-click pick that bypasses the name search is logged as a distinct `"pick"` entry so replay reproduces it exactly rather than re-running a search that could resolve differently.
- **`ffbot/draft_sync.py`** — Optional, lowest-priority: polls `league.draft_results()` on a daemon thread since Yahoo's API can't *make* picks and may not even be approved by draft day. Manual entry always wins over sync. The background thread only reads from Yahoo and pushes onto a thread-safe queue; `apply_synced_picks()` (synchronous, main-thread) does the actual `DraftState` mutation — `DraftState` must never be touched off the main thread.
- **`ffbot/names.py`** — Two deliberately separate matchers: `match_board_to_yahoo` is a strict, human-reviewed cascade (exact → position → name-only → initial → fuzzy-with-margin) meant to run once before the draft via `scripts/draft_export.py --yahoo-players`; `search`/`search_scored` is a permissive prefix/subsequence matcher for the live TUI where a few keystrokes must resolve fast. Don't reuse one for the other's job — a wrong silent match pre-draft is worse than an unmatched player, while `difflib` ratio scoring is a poor fit for "type 4 letters and hit enter."
- **`scripts/draft_export.py`** — Writes the board to `draft/` (CSV, plain-text rankings, per-position text, cheatsheet) for pasting into Yahoo's manual custom pre-draft rankings UI — there is no API for setting it. So if you're ever disconnected on draft day, Yahoo's autopick still follows your board. Optionally reconciles board names against a dumped Yahoo player list and writes `draft/yahoo_ids.json`, which `--sync` needs.

## Design invariants worth preserving

- **Config, not code, for tuning.** New thresholds/weights belong in `config.yml` + the corresponding dataclass in `ffbot/config.py`, not hardcoded.
- **The optimizer must stay exact and deterministic.** Any change to `ffbot/lineup.py` should preserve: (1) exact optimality (not a heuristic), (2) stable output across runs (ties break on player name), (3) minimal-move preference among equally optimal assignments. Both the in-season path and the draft assistant depend on this.
- **Drops are the one in-season action guarded by explicit policy**, not a confirmation step, because the agent is meant to act unattended. New irreversible actions should get the same treatment: a `Verdict`-returning policy function with the reason surfaced, not a silent allow/deny.
- **Refresh-token persistence must happen before any other work in a run.** Never reorder `refresh_access_token` so that persistence could be skipped by an early return or exception.
- **Never log or print a token.** `TokenSet.__str__` deliberately redacts; keep that pattern for any future secret-bearing object.
- **`scripts/draft.py`, `scripts/week_report.py`, and `scripts/gui.py` must stay importable and runnable with no network and no `yahoo_fantasy_api`/`requests` at module level.** Only `--sync` (draft) touches Yahoo today, and it imports those lazily inside `_build_sync` — the offline paths must keep working even if the Yahoo API was never approved. `week_report.py`'s own network-touching step (researching weather/injuries/Vegas) is deliberately kept *outside* the script entirely, in the `/gameday` command — see `ffbot/week.py`'s module docstring.
- **Pre-draft ID matching vs. live TUI search are different problems** (see `ffbot/names.py` above) — don't collapse them into one matcher.
- **Season-long valuation always passes `week=None`** to `optimize()` — `draft.need()` is always a season-long decision. `week.waiver_candidates()`/`rank_streamers()` now accept an optional real `week` too, but only to zero/exclude a candidate's *this-week* contribution when they're on bye that week — the rest-of-season side of any blend stays on the season board and must never be zeroed by it. Weekly *lineup* decisions (`week.build_week_brief`) are the one place a real week number was always correct and required.
- **`scripts/gui.py` is single-threaded on purpose.** The draft session is one shared, mutable `UiState` with no lock — serializing every HTTP request through one thread (`http.server.HTTPServer`, not `ThreadingHTTPServer`) is what keeps `DraftState` main-thread-only (see `ffbot/draft_sync.py`'s existing invariant on this) without adding one. Don't switch it to a threading server without adding real synchronization.
- **`config.yml` is never rewritten by code.** It's hand-narrated with comments a YAML round-trip would destroy. Anything that needs to *write* settings (the GUI's Settings page) writes to the gitignored `config.local.yml` overlay instead (`_deep_merge`d on top at load time) — never add a code path that calls `yaml.safe_dump` against `config.yml` itself.

## Project status

See [README.md](README.md) for the full status summary. Short version: auth, lineup optimization, drop/FAAB policy, the full draft assistant, the in-season weekly manager's M1 (manual `roster.yml` baseline — see [docs/INSEASON.md](docs/INSEASON.md)), and the web GUI are built and tested (679 tests).
