# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ffbot` is two tools around one Sleeper fantasy football team, plus a web GUI on top of both:

1. **In-season manager** — the weekly start/sit + waivers + streaming brief (`scripts/week_report.py`, driven by the `/gameday` command), built on the same optimizer as the draft assistant. A manual `roster.yml` baseline works with no Sleeper account at all; a live Sleeper-fetch route (`roster_source: sleeper`) is built and working — see [docs/INSEASON.md](docs/INSEASON.md) for the full design.
2. **Live snake-draft assistant** — a keyboard-driven, fully offline TUI (`scripts/draft.py`) that recommends picks in real time using the same optimizer as the in-season manager, with optional live pick sync from a Sleeper draft.
3. **Web GUI** (`scripts/gui.py`, `ffbot/webapi.py`, `web/`) — a local, dependency-free `http.server` front end exposing both of the above as browser pages, sharing the identical compute layer and the identical `draft_log.jsonl`/lineup-state files as the two CLIs. The weekly page is a read-only assistant landing page — it auto-loads the current week's exact live Sleeper state (roster, lineup, waiver priority, every rival's roster) plus researched intel and renders recommendations; nothing on it is hand-edited.

## Commands

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt   # Windows; .venv/bin/pip on macOS/Linux

pytest                                            # run the full suite
pytest tests/test_lineup.py                       # one file
pytest tests/test_lineup.py::test_name -v          # one test

.venv/Scripts/python scripts/whoami.py --username <you>   # discover your Sleeper league_id/roster_id, no credentials needed

.venv/Scripts/python scripts/draft_export.py --board rankings.csv    # pre-draft board -> Sleeper pre-draft-rankings export

.venv/Scripts/python scripts/week_report.py --week 3 --stream K DEF --waivers             # weekly brief (see docs/INSEASON.md)
```

## Architecture

### Sleeper client

`ffbot/sleeper/` is the read-only, unauthenticated HTTP client for Sleeper's public API — no OAuth, no credentials, no token rotation to manage, unlike the Yahoo integration this repo originally targeted (see git history before this package existed if you need the shape of what an authenticated version looked like).

- **`ffbot/sleeper/client.py`** — `SleeperClient`, stdlib `urllib` only. Two tiers: **documented** endpoints (state, user, leagues, rosters, users, matchups, transactions, traded picks, drafts, draft picks, the players dump, trending) are stable; **undocumented** ones (`season_projections`/ADP, `ownership`%) were verified live during scoping but are unsupported by Sleeper and could change without notice — every caller of those two MUST treat a fetch failure as "no data this run," never let it propagate uncaught (see `ffbot/projections/sleeper.py`/`ffbot/board.py`'s `board_points_source` for the pattern). TTLs are per-endpoint, reflecting how fast each thing actually changes (rosters move on waiver day, league settings almost never do); `draft()`/`draft_picks()` are deliberately NEVER cached at all — a live draft's poll loop needs a real-time read, not a stale one.
- **`ffbot/sleeper/cache.py`** — TTL-sidecar cache (`.meta` file records fetch time; injectable `now` for tests), the league-client sibling of `ffbot/projections/cache.py` — deliberately not a reuse of `ffbot/history/fetch.py`'s immutable-source cache, since league state changes constantly and a cache hit must be able to expire.
- **`ffbot/sleeper/models.py`** — Translates Sleeper's word-based `injury_status` (`Questionable`, `Doubtful`, `IR`, ...) onto this repo's existing single-letter status vocabulary (`models.STATUS_OUT`/`STATUS_QUESTIONABLE`), which traces back to Yahoo's original codes and is kept unchanged so `lineup._must_bench`/`policy.can_drop`/`history/index.py`'s injury mapping never need a second vocabulary. Sleeper's own flex-slot names (`FLEX`/`SUPER_FLEX`/`WRRB_FLEX`/`REC_FLEX`) are registered directly in `ffbot.models.SLOT_ELIGIBILITY` instead — no translation needed there, since Sleeper's `roster_positions` values match those names verbatim.

### Live game conditions and markets

Two more no-auth, unauthenticated live clients (commit a9c2866), both feeding the weekly spice signals — `ffbot/sleeper/` above is about roster/league identity, these two are about the WEATHER/ODDS half of the picture.

- **`ffbot/live/`** — `schedule.py` fetches this week's real NFL schedule (`this_week_games`, always `refresh=True` — a live week's row can change under flex scheduling); `weather.py` fetches Open-Meteo forecast weather per stadium, skipping domes entirely; `conditions.py` (`fetch_conditions`) merges both plus Kalshi game odds (see below) into `{team: GameInfo}`, then `merge_conditions` layers a human's hand-typed `weekly/week-NN.yml` research UNDER it — a hand-typed value always wins, whole-entry. `cache.py` is the shared TTL sidecar (`game_conditions.cache_ttl_minutes` in config.yml). Gated by `game_conditions.weather_source`/`odds_source` (`"off"` by default in code, `"open_meteo"`/`"kalshi"` in the shipped config.yml); a failed fetch on either source degrades independently with a surfaced alert, never a crash — same live-seam contract as everything else in this repo.
- **`ffbot/markets/`** — `kalshi.py` is the raw, series-agnostic Kalshi HTTP client (`https://api.elections.kalshi.com`, no auth needed to read markets); `kalshi_nfl.py` layers NFL semantics on top: `game_odds` (implied team totals from `KXNFLTOTAL`/`KXNFLSPREAD`, live at EVERY spice level, feeding `ffbot.live.conditions`) and `player_prop_probabilities`/`draft_signal`/`weekly_signal` (per-player anytime-TD and season-rank markets, spice level 4 ONLY on both the weekly and draft paths — `SeasonConfig.kalshi_weight`/`DraftConfig.kalshi_weight` — since Kalshi's NFL markets launched September 2025, zero overlap with this repo's entire backtest window). Both fetch-gated on the relevant weight being nonzero (`ffbot/report.py`, `scripts/draft.py`) — the "don't even ask" pattern every optional live seam in this repo uses.

### In-season path

`scripts/whoami.py` calls `ffbot.sleeper.client.SleeperClient` directly (no auth step at all) to discover `league_id`/`roster_id`/`roster_positions`/`scoring_settings`, printed for you to paste into `config.yml`'s `sleeper:` block (`scripts/init_league.py` does this automatically, into `config.local.yml` and `league.yml` — see `ffbot/sleeper/scoring_import.py`). `--sync` (see the draft assistant path below) needs a second thing beyond `sleeper.league_id`: `draft/sleeper_ids.json`, the board-key -> Sleeper player id map `scripts/draft_export.py --reconcile` produces. `init_league.py` builds that too, best-effort, in the same run — if `draft.board_csv` is already configured and loadable (rare on a first-ever bootstrap, since the FantasyPros CSVs are still a manual download at that point) it fetches Sleeper's players dump and writes the map immediately, so sync is live the moment the script finishes rather than after a second command you have to remember; a board that isn't ready yet just skips this step silently, and the printed "Next steps" explain how to finish it later. `scripts/week_report.py` is the weekly runner: `roster_source: file` (the default) works from a hand-maintained `roster.yml`; `roster_source: sleeper` fetches your live roster instead — see [docs/INSEASON.md](docs/INSEASON.md) for the full design and the roster-source routes.

- **`ffbot/sleeper_roster.py`** — The M3 roster route: your live Sleeper roster (names, teams, injury status, ownership%), replacing `roster.yml`'s `players:` list as the identity source when `roster_source: sleeper`. `roster.yml` stays relevant even then — read as an optional per-player FLAG overlay (`undroppable`/`keeper_round`/`note`/`blocking`, human judgment no platform can supply), merged onto the live roster by name via `merge_flags`. `fetch_my_roster` joins a roster's `player_id` list against the full players dump for identity; `apply_sleeper_identity` sets `Player.status`/`percent_owned` as the BASE layer that `week.apply_status_overrides` (run afterward, unchanged) can still win over — a hand-researched `weekly/week-NN.yml` entry beats a live-but-possibly-stale API field, never the reverse. `ffbot.roster_source.load_roster`'s `entries` parameter is the seam this plugs into; everything downstream (matching against weekly/provider/fallback rows, bye backfill) runs completely unchanged. `starters_slot_map` additionally zips a roster's `starters`/`reserve` arrays against the league's own ordered `roster_positions` (from `SleeperClient.league()` — NOT `cfg.roster_positions`, which has lost that ordering) to learn each player's CURRENT slot in the Sleeper app; `apply_sleeper_identity`'s `roster_positions` parameter, when given, writes that onto `Player.selected_position` (translated through `models.equivalent_slot` so a Sleeper spelling like `FLEX` lands on whatever spelling the configured layout uses) — the live lineup baseline `report.load_everything`'s `slots_source` flag signals downstream, replacing `weekly/lineup_state.yml` entirely on this route.
- **`ffbot/config.py`** — All tunable behavior (scoring weights, drop protections, draft valuation, weekly spice) loads from `config.yml` via nested dataclasses (`SleeperConfig`, `RosterSourceConfig`, `ProjectionSourceConfig`, `DropPolicyConfig`, `DraftConfig`, `SeasonConfig`). The intent is that tuning strategy is a config edit, never a code change. Waivers are always modeled as rolling-priority — there is no FAAB support (`FaabConfig`/`LeagueScoring.waiver_type` were removed; a leftover `league.yml` `waiver_type:` key other than `rolling` now just emits a `DeprecationWarning`). `Config.roster_positions` also seeds the draft assistant's slot layout before a real Sleeper connection exists. `SeasonConfig`'s primary dial is `spice_level` (1-4 as of the B7 rescale — was 1-5; resolved by `SeasonConfig.from_spice_level` into over a dozen underlying weights, including structural ones like `waiver_value_mode`/`denial_weight` that B7 folded into the ladder) rather than the raw weights themselves — weather/Vegas alone mostly agree with consensus on a calm week, so a single named level is what keeps "how contrarian" legible without hand-tuning a dozen numbers, and any one field can still be overridden individually on top of the preset. See [docs/SPICE.md](docs/SPICE.md) for the full feature-by-level breakdown. `Config.load` additionally merges an optional sibling `config.local.yml` on top (deep-merged; see `_deep_merge`) — the GUI's Settings page writes there instead of `config.yml`, whose comments a YAML round-trip would destroy. The old top-level `league_id`/`team_key` (Yahoo concepts) are gone, replaced by `sleeper: {league_id, username, roster_id}`; `Config.from_dict` still honors the old `league_id` key as a deprecated fallback into `sleeper.league_id`. `DraftConfig.order` (`"snake"`/`"linear"`) and `LeagueScoring.my_opponent`/`SeasonConfig.denial_opponent_boost`/`denial_seed_window` are documented in [docs/SETUP.md](docs/SETUP.md)'s configuration reference.
- **`ffbot/models.py`** — `Player` fields and the status/slot vocabulary trace back to Yahoo's `yahoo_fantasy_api.Team.roster()` shape (this repo's original target) and are kept even though the live source is now Sleeper — Sleeper's own client translates onto this one vocabulary at the boundary (`ffbot/sleeper/models.py`) rather than a second vocabulary spreading downstream. `SLOT_ELIGIBILITY` carries both Yahoo's `"/"`-joined scheme AND Sleeper's standalone flex names side by side (additive, not a replacement — a roster built from either source resolves slots correctly). `STATUS_OUT`/`STATUS_QUESTIONABLE` classify the shared vocabulary into hard-bench vs. discount-but-start. `team` exists because the weekly weather/Vegas signals need it to look up a player's game.
- **`ffbot/lineup.py`** — Deterministic, offline optimizer (no LLM — it must be fast and predictable for a Sunday-morning deadline, and fast enough to call thousands of times during a live draft, see below). Modeled as bipartite matching: startable players form a transversal matroid, so taking players in descending projected-score order and greedily augmenting (Kuhn's algorithm, `_augment`) yields the exactly optimal lineup, not just a good one. A second matching pass then picks *among* equally-optimal assignments the one requiring the fewest actual position changes, so the optimizer doesn't churn equivalent slots for zero score gain. This module is the shared core both the in-season path and the draft assistant build valuation on top of. Note that `optimize()` never mutates a `Player`'s `selected_position` to reflect where it just placed them — the new slot exists only as the first element of each `assignments` tuple, since `optimize()` is a pure function and writing the change is the caller's job; `week.py`'s lineup-state persistence exists specifically to bridge that gap across runs. `LineupPlan.as_lineup_write()` produces the `{player_id, selected_position}` shape a hypothetical future write path would need — Sleeper's public API has no write capability at all, so nothing in this repo actually calls it today; kept as documentation of the shape, not evidence a write path exists.
- **`ffbot/policy.py`** — Guardrails specifically on *drops*, since lineup changes are freely reversible but a drop is not (another manager can claim the player instantly). Every rule is phrased as "would I regret this Monday?": undroppable flags, a `never_drop` list, early-draft-round protection, high-ownership protection, and a refusal to drop anyone only *temporarily* unavailable (bye week, Questionable). `policy.droppable()` sorts by `percent_owned`, which is real, live signal under `roster_source: sleeper` (from Sleeper's ownership-research endpoint — see `ffbot/sleeper_roster.py`) but stays `None` for every player under the manual `roster.yml` route; callers on that route must pre-filter to a sensible candidate pool (e.g. the optimizer's own bench) before calling it, not hand it the full roster — see the comment in `week.waiver_candidates` for the bug this caused when that wasn't done (it suggested dropping a starting QB).
- **`ffbot/week.py`** — The in-season analog of `ffbot/edge.py`: status overrides, weather (`data/stadiums.yml` for the dome gate; wind/precip discount pass-heavy positions, RB gets partial relief, DEF is untouched since bad weather tends to help defenses), a venue-disruption discount for neutral-site/international games (`GameInfo.venue` overrides the usual home/away stadium lookup; `international` gates the off-by-default `venue_disruption_weight`), Vegas implied-total tilt (inverted for DEF — the opponent's total is what matters, not the team's own), and a `volatility_weight`/`upside_lean_weight` spice pair that exists specifically so a close start/sit call can still go to the higher-ceiling player on a calm week with no weather/Vegas story — without it the system would mostly just re-derive consensus. All weights are fractions of `decision_scale` (the point spread across the roster), same reasoning as `edge.decision_scale`. `waiver_candidates` takes a `pool: Board` — normally the frozen season board, but `ffbot.report.load_everything` builds a real rest-of-season-rescaled copy (`LoadedReport.ros_board`, via `ffbot.board.rescale_board_points` + `ffbot.projections.ros_rows`) when a live projection source is configured, so `ros_gain`/`hold_margin`/`drop_cost` read genuine live numbers with zero change to this module's own valuation math — see `ffbot/board.py`'s note on `rescale_board_points` below. It also takes an optional `week` to zero a bye-week candidate's this-week contribution (`rank_streamers` excludes them outright — a streamer who can't play isn't a candidate at all). DEF team identity is resolved through `names.defense_key` before any lookup (`_resolve_team`), because board defenses routinely carry a blank or full-city-name `team` field rather than a clean abbreviation (Sleeper's own defense identity has no such problem — its `player_id` IS the team abbreviation — but the FantasyPros-sourced board still does).
- **`ffbot/denial.py`** — Tactical denial: `threat()` scores a rival 0..1 by playoff-bubble seed distance, plus two additive, individually no-op boosts — `opponent_boost` when the rival is `league.yml`'s `my_opponent` this week, and a `seed_window` proximity boost (gated by `is_playoff_push`, the final few weeks of `regular_season_weeks`) for a rival near your own seed. Needs `league_rosters.yml` (rival rosters — see `scripts/import_league_rosters.py`'s `--live` flag, which fetches this straight from Sleeper's rosters/users endpoints via an exact `player_id` join, no fuzzy matching needed) and `league.yml`'s `teams:` standings; either missing collapses every function here to an exact no-op. `denial_value`/`denial_candidates`/`handoff_risk` all discount a rival's raw `need()` against `best_available_by_position`'s "next name on the wire" — a rival's real loss from being denied a player is `need(candidate) - need(next available alternative)`, not the full vs-replacement gain, so a fungible position (any deep bench spot, K/DEF nearly always) collapses toward zero regardless of how big a hole the rival's roster shows; a genuinely scarce player (no comparable alternative on the wire) keeps full value. `denial_candidates` also skips any position in `cfg.season.stream_positions` outright (K/DEF by default — definitionally non-deniable, the wire refills them every week) and reports MAX(threat × gain) across rivals, not a sum (a denied player lands on at most one roster, so summing the same hole across every team that has it double-counts a single spot) — `denial_value` keeps the sum, since it feeds *claim urgency* (additive contestedness), a genuinely different question. This was a real bug: pre-fix, a demo league with several rivals missing K/DEF entirely produced five simultaneous "pure denial" waiver-claim rows on backup kickers/defenses.
- **`ffbot/gameplan.py`** — The unified weekly recommendations engine behind both the GUI's Recommendations panel and `scripts/week_report.py`'s `--waivers` sections: `build_gameplan(loaded, week_num, players, ...)` values every candidate off ONE pool (`loaded.ros_board or loaded.board` — fixes a real bug where denial used to be valued off a different board than waivers), folds streaming and denial into ordinary add/drop rows instead of separate categories (a K/DEF need is *detected*, not dumped as a flat N-per-position list; a denial motive is a `reason`, via `denial.denial_candidates` merged in — capped at `SeasonConfig.denial_row_limit` (default 1), since denial is meant to be rare — and `policy.can_deny_claim` gated exactly once here instead of duplicated per caller), and bakes recommended free-agent adds into a coherent post-pickup `base_plan` — each waiver CLAIM instead gets its own `ClaimConsequence` ("if it clears: start at WR over X (+2.1)"), computed by re-optimizing the post-add roster with that one claim substituted in. `pair_moves` is the presentation-layer read of `lineup.LineupPlan.moves`' raw diff into human-shaped `SwapLine`s (paired swaps, first-class slot shifts like `WR -> FLEX`, "replaces dropped X") — `lineup.optimize()` itself is untouched. Opponent awareness is first-class, not just a QB/WR special case: `week.opponent_overlap` prices same-team stacking with the live head-to-head opponent's actual started lineup (`LoadedReport.opponent_starters`, see `ffbot/sleeper_standings.py`'s `fetch_opponent_starters` below) as a discount, and DEF-vs-their-skill-players as leverage (a bonus), via `SeasonConfig.opponent_correlation_weight` (judgment-set, exact no-op at 0.0 or with no live fetch). A recommended drop's own hand-off risk (a rival, opponent first, could claim who you cut) reuses `denial.handoff_risk` directly — the drop chosen for both the coherent multi-add transaction set AND every ordinary waiver claim is ordered by `hold_margin + handoff_risk` (fungible over scarce), and each row's `net`/`drop_reason` is corrected against whichever drop actually got assigned, not the single shared one `week.waiver_candidates` originally guessed. Pure composition, no network — `webapi.weekly_report_json` and `scripts/week_report.py` both call it and no longer duplicate any of this.
- **`ffbot/roster_source.py`** — Turns `roster.yml` (bare names — no slots; the optimizer decides those fresh every run) into `Player`s, matched against weekly FantasyPros projections when available and the existing season-long draft board (rescaled to a per-week baseline) otherwise, so the report runs every week without requiring a fresh download each time. A roster name that matches nothing is always surfaced, never silently dropped — the dangerous failure mode is a real rostered player quietly vanishing from every recommendation. `load_roster`'s `entries` parameter, when given, REPLACES `load_roster_entries(roster_path)` as the identity source — the seam `ffbot.sleeper_roster.merge_flags` plugs into for the live-roster route. Also owns lineup-state persistence (`load_lineup_state`/`save_lineup_state`/`apply_lineup_state`) — see the `lineup.py` note above for why this exists.
- **`ffbot/projections/`** — Live weekly + rest-of-season projections, the fix for `week_report.py`'s old dead `--proj` hatch and `ros_blend`'s once-frozen "ROS" side. `sleeper.py`'s `fetch_weekly_rows` returns rows in `board.read_fantasypros`'s exact shape (name/team/position/points/bye/`stats`, a real `ffbot.scoring.StatLine`) so `board.apply_league_scoring` recomputes every projection under the league's actual rules — the same treatment board CSVs already get, and it closes real scoring gaps FantasyPros' own exports can't (2-point conversions, missed PATs). `fetch_season_points_rows` is the sibling used for the DRAFT board's points overlay (see `ffbot/board.py` below) — deliberately NOT a `StatLine` reconstruction, since Sleeper's season-grouped stat shape diverges from the weekly one for K/DEF specifically (bucketed FG-distance/points-allowed counts, not per-kick/per-game figures); it returns Sleeper's own `pts_ppr` as a plain consensus number instead, same footing FantasyPros' points already sit on. `__init__.py`'s `ros_rows` sums correctly-scored weekly numbers across a real week range into a genuine rest-of-season total (never counting an already-played week, since the caller supplies `from_week`) — the seam `ffbot.report.load_everything` uses to build `ros_board`. Controlled by `config.yml`'s `projection_source:`/`draft.board_points_source:` blocks (both default off — exact no-op until switched on); a failed fetch always falls back to the frozen board and surfaces a loud alert, never fails silently.
- **`ffbot/report.py`** — `load_everything(...)`: the shared loader behind both `scripts/week_report.py` and the GUI's weekly endpoint (config, weekly intel, board, matched roster, live roster identity, live weekly + rest-of-season numbers, live league rosters). Raises `ReportError` (never `SystemExit`) so the GUI can catch it; `scripts/week_report.py`'s own `load_everything(args)` is a thin wrapper that turns `ReportError` back into the `SystemExit` the CLI has always used. Four independent live-data seams, each with its own alert list and never-crash fallback: `projection_source`/`projection_alerts` (weekly + ROS numbers), `roster_source`/`roster_source_alerts` (roster identity — plus `slots_source`, set to `"sleeper"` only when a live lineup baseline was actually built), and `league_rosters_source`/`league_rosters_alerts` (the other 11 teams' rosters, via `ffbot.league_rosters.fetch_league_rosters` — falls back to the `league_rosters.yml` snapshot on failure). All Sleeper-touching branches share ONE `SleeperClient` (built once, up front, `force_refresh=refresh` when the caller wants the GUI's "Refresh" semantics — see `SleeperClient.__init__`), so a run touching roster identity, slots, and league rosters together still costs one HTTP request per distinct endpoint, including the ~5MB players dump. `ros_board` is a SEPARATE field from `board`, never a replacement — `board` must stay a true full-season total for `roster_source.season_board_rows`'s fixed-divisor contract; substituting a partial-season ROS total there would silently understate every fallback-priced candidate's weekly rate.
- **`ffbot/webapi.py`** — JSON serializers for the GUI: `draft_state_json` mirrors every section of `draft_ui.render()` (plus `header.survival_to_pick`, the pick every `survival` in the payload is measured to, so the GUI can label the column instead of showing a bare percentage); `weekly_report_json` is the read-only weekly page's entire contract — enriched `lineup.assignments`/`bench`/`ir` (slot/position/team/status/opponent/kickoff, bench "why benched," the third IR group `lineup.optimize()` excludes from the other two entirely), a read-only `intel` block (roster-matched player notes + matchup rows, reusing `weekly_editor.editor_json_from_intel`'s transform), and `league_rosters`/`slots_source`/`week_source`/`refreshed` badges. `commit_lineup` (and the lineup-state read/write it gates) is skipped entirely whenever `loaded.slots_source == "sleeper"` — live Sleeper starters already ARE the baseline there, so there's nothing to commit; the GUI never passes `commit_lineup=True` at all anymore (that was the old "Commit this lineup" button), only `scripts/week_report.py`'s file route still uses it.
- **`ffbot/notify.py`** — The one OUTBOUND live seam (every other live seam here is inbound): push notifications for `scripts/autorun.py`'s unattended runs, held to the identical never-raise/alert-on-failure contract. `send(cfg, title, body, *, runner=None, opener=None)` — `"ntfy"` (a free, no-signup phone push via ntfy.sh; the topic name is the secret, so it lives in `config.local.yml`, never `config.yml`) and `"toast"` (a local Windows notification via PowerShell) are independent channels, `"both"` fans out, `"off"` is an exact no-op.
- **`ffbot/roster_editor.py` / `ffbot/weekly_editor.py`** — No longer wired to any GUI endpoint (the weekly page is read-only now — see the Web GUI description above); both survive as read/write helpers `scripts/demo_season.py` uses to generate demo fixtures, and `weekly_editor.editor_json_from_intel` is also the read-side transform `ffbot/webapi.py`'s `intel.matchups` reuses directly. `weekly_editor` is deliberately matchup-centric (one row per game, not per team) even though `week.WeeklyIntel.games` stores each game twice, mirrored — editing the raw per-team shape invites the two sides drifting apart (wind entered on one team's row, not the other); the write side mirrors both sides from a single row so that can't happen.
- **`ffbot/draft_store.py`** — File-backed archive/save/load for the draft log, used by both `scripts/draft.py`'s local `reset`/`save`/`load` commands and the GUI's equivalent buttons. Pure I/O, deliberately outside `draft_ui.handle()` (which stays a pure state machine).
- **`ffbot/intel.py`** — Loads `draft/intel.yml`, pre-draft only. `ffbot/week.py` has its own parallel loader (`load_weekly_intel`/`WeeklyIntel`/`WeeklyPlayerIntel`) for `weekly/week-NN.yml` rather than reusing this module directly — the two files carry different shapes (the weekly one also has a `games:` section for kickoff time/weather/Vegas/venue that has no draft-time analog) — but both are held to the identical factual/speculative contract (see [docs/DRAFT.md](docs/DRAFT.md) and [docs/INSEASON.md](docs/INSEASON.md)) and both use the same unmatched-name philosophy: `names.normalize_name` matching, a fuzzy suggestion on a miss, never a silent crash or a silently dropped player, and a missing file leaves the board/roster bit-identical.

### Draft assistant path

`scripts/draft.py` is a thin keyboard/render shell around a pure state machine, so the interaction loop needs no pty to test. Everything runs offline against a pre-built board; `--sync` (optional live pick sync from a Sleeper draft) needs no auth and no API approval, so it's a real, working convenience now rather than the lowest-priority maybe-someday feature it was under Yahoo.

- **`ffbot/board.py`** — Loads and values the frozen pre-draft board from FantasyPros CSV exports (`read_fantasypros` sniffs headers across their rankings/ADP/projections products; `_merge_csv_rows` combines multiple exports by normalized name+position). Replacement level is *derived*, not assumed: it scales the league's starting slots by `num_teams` and runs `lineup.optimize()` over the whole player pool — the matroid-exchange property means truncating each position to its top `S_p` candidates first is exact, not approximate, and makes the call ~8x cheaper. VOR (value over replacement) and tiers (gap-based, normalized by each position's median gap so it's scale-free across QB vs. K) are computed once and frozen for the draft. `load_board`'s `extra_points_rows` (from `draft.board_points_source: sleeper`, see `ffbot/projections/` above) overlays live Sleeper points onto the board while FantasyPros' CSVs still supply everything Sleeper's endpoint doesn't carry — ADP, bye weeks, cross-site ADP spread — via `_apply_points_overlay`, which runs strictly AFTER `apply_league_scoring`, not folded into the CSV merge: an earlier version that folded it into the merge let a CSV row's `stats` field silently clobber the overlay's points the moment league scoring was configured (a real bug caught by `tests/test_board.py::TestLoadBoardExtraPointsRows::test_overlay_wins_even_when_csv_carries_a_real_stat_line_under_league_scoring` — read that test before touching this ordering). `rescale_board_points` is the same overlay mechanism applied a second time, to an already-built `Board` rather than raw CSV rows — the seam `ffbot.report.load_everything` uses to build a rest-of-season-real `ros_board` (see `ffbot/week.py` above) without `week.py`'s valuation functions needing any live-data override hook of their own. `_finalize_board` is the shared tail (replacement level, tiers, `BoardPlayer` construction, VOR-sorted ranking) both `load_board` and `rescale_board_points` call.
- **`ffbot/draft.py`** — Live pick math: snake order (`pick_number`/`round_and_slot`, both order-aware — `order="snake"` reverses direction each round, `"linear"` doesn't), ADP survival probability (`Normal(adp, sigma)`, conditioned on already surviving to the current pick), and `DraftState` (the pick log + roster + `order`). Valuation (`need`/`value`) is built on `lineup.optimize()` rather than hand-tuned positional weights: `need` is the marginal season-long optimal-lineup points gained by drafting a candidate vs. a replacement-level player at that position, given the roster so far; `value` adds a depth term (clamped VOR) so late-round players aren't all valued at zero once starters are full. `recommend()` scans the *entire* remaining pool every pick (cheap enough — tens of ms against 500+ players) rather than shortlisting. Every survival number is measured to `DraftState.next_my_pick_after(current)` — my next turn STRICTLY after the current pick — never `next_my_pick()`, which returns the current pick itself while I'm on the clock and made `survival()` return a meaningless 1.0 for every candidate on exactly the picks I had to decide. `alerts()` is deliberately three kinds only, each filtered through `_alert_positions` (a position I've capped out on, deferred this round, or am already deeper than my target at can't change my next pick, so it doesn't get a line) and capped at `alert_limit`: `RUN` (opponent picks only — my own roster is not a signal about what the room is doing), `WAIT` (best player available at a position now vs. best one likely to survive to my next turn, in projected points), and `BYE` (via the same optimizer, comparing against a week=`None` baseline so it stays quiet early when the roster is mostly empty). Two tier-based alerts were removed for firing at nearly every position on nearly every pick — see the `alerts()` docstring and [docs/DRAFT.md](docs/DRAFT.md) for why `WAIT` replaces both.
- **`ffbot/edge.py`** — Contrarian valuation terms layered on `draft.need`: round-ramped risk appetite (`risk_ramp` — floor early, ceiling late), volatility from cross-site ADP disagreement (`adp_spread`, ranked within position), QB↔pass-catcher stacking, ADP arbitrage, and a deficit-urgency roster-balance term. Every weight defaults to 0.0 (exact no-op; the aggressive values live in `config.yml`), weights are *fractions of the per-pick decision scale* (never absolute points — round-1 gaps are 100+ points, round-12 gaps are 2-3), and K/DEF are excluded from every term (`EDGE_EXCLUDED_POSITIONS` — each term misreads them; the comment there explains why per-term). `recommend()` additionally enforces `position_caps` (hard), defers K/DEF until the last two rounds, and force-fills empty dedicated starting slots when picks run out.
- **`ffbot/intel.py`** — Loads researched player intel from `draft/intel.yml` (produced by Claude Code web research pre-draft — see [docs/DRAFT.md](docs/DRAFT.md) for the cadence). Matched by `names.normalize_name`; unmatched entries warn with a fuzzy suggestion, never crash; a missing file leaves the board bit-identical. `upside` feeds the value function via `upside_weight`; `note` lands verbatim in the recommendation WHY column, so notes are written as short plain English.
- **`ffbot/draft_ui.py`** — Pure `handle(state, line) -> UiState` / `render(state) -> str`, no terminal dependency; both `scripts/draft.py`'s terminal loop and `scripts/gui.py`'s HTTP handler call the same `handle()`. `reset`/`save <name>`/`load <name>` are intercepted *before* `handle()` (see `scripts/draft.py`'s `handle_local_command`), since they touch the filesystem (`ffbot/draft_store.py`) and `handle()` must stay pure. Every typed command is appended to a resumable log (`draft_log.jsonl`); a GUI row-click pick that bypasses the name search is logged as a distinct `"pick"` entry so replay reproduces it exactly rather than re-running a search that could resolve differently.
- **`ffbot/draft_sync.py`** — Optional live sync from Sleeper's draft picks, needing no auth. Manual entry always wins over sync. `DraftSync` polls `SleeperClient.draft()` for a changed `last_picked` timestamp first, and only fetches the (larger) full `draft_picks()` list when something actually moved — verified live against a real completed Sleeper draft during development (180 real picks synced correctly, `mine` resolved via `roster_id`). The background thread only reads from Sleeper and pushes onto a thread-safe queue; `apply_synced_picks()` (synchronous, main-thread) does the actual `DraftState` mutation — `DraftState` must never be touched off the main thread.
- **`ffbot/names.py`** — Two deliberately separate matchers: `match_board_to_platform` is a strict, human-reviewed cascade (exact → position → name-only → initial → fuzzy-with-margin) meant to run once before the draft via `scripts/draft_export.py --reconcile` (against a live Sleeper players-dump fetch) or `--sleeper-players-file` (a saved dump, for reproducible/offline runs); `search`/`search_scored` is a permissive prefix/subsequence matcher for the live TUI where a few keystrokes must resolve fast. Named generically, not `match_board_to_sleeper`: most of its callers (`ffbot.history.names.match_actuals`, `scripts/projections_check.py`, `scripts/import_league_rosters.py`'s `--paste` route) feed it synthetic ids for a coverage/reconciliation check, not a real platform's player list. Don't reuse one matcher for the other's job — a wrong silent match pre-draft is worse than an unmatched player, while `difflib` ratio scoring is a poor fit for "type 4 letters and hit enter."
- **`scripts/draft_export.py`** — Writes the board to `draft/` (CSV, plain-text rankings, per-position text, cheatsheet) for pasting into Sleeper's pre-draft rankings UI — there is no API for setting it. So if you're ever disconnected on draft day, Sleeper's autopick still follows your board. `--reconcile` fetches Sleeper's players dump live (the only place this script touches the network, and only when asked) and writes `draft/sleeper_ids.json`, which `--sync` needs; `--sleeper-players-file` takes a previously-saved dump instead, for reproducible/offline runs (e.g. tests).

### Backtesting

See [docs/BACKTEST.md](docs/BACKTEST.md) for the full design (data sources, baselines, statistics protocol, leakage register, B1–B7 milestones). B1–B7 are built — the weekly lineup, draft, and waiver/streaming paths can all be replayed against real NFL seasons and graded, via `scripts/backtest_{lineup,season,weather,tune,draft}.py`. B7 re-audited both ladders on the freshest data, rescaled `spice_level` from 1-5 to 1-4 with new user-facing semantics (1 blind-baseline, 2 tactics-only, 3 evidence-backed default, 4 use-at-your-own-risk), folded five previously-unladdered draft structural terms into `DRAFT_SPICE_PRESETS`, fixed a real B5-era harness bug (`backtest_draft.py` was silently discarding `config.yml`'s own `position_targets`/`position_caps` per cell), and measured VOR-chalk drafting's value over blind ADP directly (+123 season pts, 95% CI excluding zero) — see [docs/SPICE.md](docs/SPICE.md). B4 found that two of `SPICE_PRESETS`' five dials (`volatility_weight`/`upside_lean_weight`) were structurally inert in every backtest before it — see `ffbot/history/signals.py` below — and re-specified `week.weather_severity`'s ramp against real data. B5 re-derived `SeasonConfig.SPICE_PRESETS` along two axes (information — weather/Vegas/usage-momentum-divergence trend — ramping levels 1→3, and deliberate variance-seeking — volatility/upside_lean/matchup_variance — ramping 3→5) and validated it on a held-out season: level 3 clears zero on both train and test, and level 4 (the production default) moved from a confirmed loss (-0.50 pts) to statistically neutral. B5 also retired `SeasonConfig.game_script_weight` for good (a follow-up experiment confirmed the harmful component but the fix only reached noise-floor, not a validated gain), added two more momentum-family signal providers (`scoring_form`, `usage_divergence`, alongside B6's `usage_form`) and wired all three trend fields into live `weekly/week-NN.yml` parsing plus `rank_streamers`/`waiver_candidates`, and built a draft-side ladder (`DraftConfig.spice_level`/`DRAFT_SPICE_PRESETS`) plus a new grader (`scripts/backtest_draft.py`) that found and fixed a confirmed-harmful live weight (`arbitrage_weight`, now retired in both the preset and `config.yml`) — though the draft ladder itself remains a first exploratory pass, not a full re-derivation, since three of its dials (`upside_weight`/`volatility_weight`/`risk_weight`) are structurally unmeasurable by `historical_board` today (no researched-intel or multi-source-ADP equivalent — the draft-side mirror of B4's own dead-dial finding). This whole layer runs on nflverse + the DynastyProcess archive, with no Sleeper dependency beyond the shared injury-code vocabulary — the Yahoo→Sleeper migration left it untouched.

- **`ffbot/history/fetch.py`** — Cache-first downloader for nflverse (box scores, schedules, injuries, weekly rosters) and DynastyProcess (the free FantasyPros ECR archive) release assets, stdlib `urllib`/`csv`/`gzip` only — deliberately not `nfl_data_py` (deprecated) or `nflreadpy` (needs Polars), since every nflverse dataset is just a CSV over plain HTTPS. Past seasons are immutable box scores, so a cache hit is trusted and never re-fetched except with `refresh=True` — the "current in-progress season" case. Compressed sources (the ECR archive) are cached still-gzipped (`.csv.gz`, ~105MB vs. ~450MB inflated) — `load_csv_rows` streams straight through `gzip.open`, so callers never see the difference. `opener` is injectable everywhere a network call happens, so nothing in `tests/test_history_fetch.py` touches the network.
- **`ffbot/history/actuals.py`** — Turns one `stats_player_week`/`stats_team_week` row into `ffbot.scoring.StatLine` and scores it via the existing, unchanged `score_statline` — real box scores let several fields FantasyPros exports can never carry (exact points-allowed instead of a season-total estimate, real per-kick FG distance bands, PAT misses, 2-pt conversions) get scored exactly instead of estimated or left unmodeled; see `StatLine`'s "Historical-replay-only fields" comment block and `docs/BACKTEST.md`'s "Scoring gaps closed" table. `week_actuals(season, week, scoring)` is the grading key every backtest metric is graded against — realized league-scored points for every player/defense that played, keyed the same way as `board.BoardPlayer.key`; it is the ONE function `ffbot.backtest` may read ground truth through (see that package's `__init__` docstring).
- **`ffbot/history/index.py`** — `as_of(season, week)` is the single point-in-time boundary: it adapts real `games.csv`/`injuries_{season}.csv` rows straight into `week.GameInfo`/`WeeklyIntel`/`StadiumInfo`, so `ffbot/week.py` needed zero changes to be replayed against history. Leakage is structural, not caller discipline — `as_of()` never fetches a results-bearing source (`stats_player_week`/`stats_team_week`/the ECR archive) at all, which `tests/test_history_index.py::TestAsOfLeakageGuarantee` asserts directly by recording every URL requested. `WeekSnapshot.game_rows` is the deliberately separate ground-truth channel (raw rows, scores included) for `actuals.py`'s post-hoc scoring — decision code must never read it, only `weekly_intel()`/`stadiums`.
- **`ffbot/history/names.py`** — `canonical_team`/`TEAM_RELOCATIONS` maps a historical team abbreviation (OAK, SD, STL, ...) onto its current franchise identity before any team-keyed lookup, so a relocated franchise's history doesn't silently split in two. `actuals_key` mirrors `board._board_key`'s convention for the common-case exact join; `match_actuals` reuses `names.match_board_to_platform`'s strict cascade (never the permissive TUI matcher) for coverage validation, on the same reasoning as that function's own docstring — a wrong silent match on ground truth is worse than an unmatched player.
- **`ffbot/history/projections.py`** — Point-in-time projections: "what a manager would have believed before kickoff," reused by both B3's replayer and B4's season simulator. `naive_projections` is a recency-weighted mean of a player's own league-scored prior weeks this season (reusing `cfg.projection.recency_window`/`recency_weight`), blended toward the prior season's per-game average early and regressed toward a positional replacement level (via `board.derive_replacement` — never hand-assumed) for a true unknown; usable back to 2009. `ecr_projections` converts the latest FantasyPros ROS-ECR scrape strictly before kickoff into points via a rank→points curve fit on seasons OTHER than the one under test — it raises `ValueError` rather than silently permitting a `fit_seasons` that includes the target season, since that's the single most likely way to fake a good backtest result. `player_pool`/`players_asof` are the historical parallel to `ffbot/roster_source.py`'s row-to-`Player` conversion, which is what lets `week.adjusted_players`/`lineup.optimize` run against real history unchanged.
- **`ffbot/history/signals.py`** — The fix for a real finding, not a nice-to-have: `week.WeeklyPlayerIntel.volatility`/`.upside` (the fields `volatility_weight`/`upside_lean_weight` read) were never populated anywhere in historical replay before this module existed, making two of `SPICE_PRESETS`' five dials silently inert — `spice_bonus` measurably returned `0.0` for every player until this shipped. A `SignalProvider` (`(season, week) -> {normalized_name: {signal: 0..100}}`) is merged onto a `WeekSnapshot` via `WeekSnapshot.with_signals()` (`ffbot/history/index.py`) — deliberately AFTER `as_of()`, not folded into it, since a form-based provider needs `stats_player_week` (a results-bearing source by the letter of `as_of()`'s leakage guarantee, even though every week it reads is safely in the past) and providers living outside `as_of()` means that guarantee never needs an exception. Four providers ship: `historical_form` (B4 — coefficient of variation / ceiling-over-median of prior-week points, feeding `volatility_weight`/`upside_lean_weight`; a stats-only proxy for whether the MECHANISM helps, not whether researched intel is any good), `usage_form` (B6 — recent WOPR vs. season average, feeding `usage_weight`; the first dial in this project's history whose train-selected weight held up, barely, on a held-out season), and `scoring_form`/`usage_divergence` (B5 — recent points vs. season average, and the gap between role-trend and points-trend rank, feeding `momentum_weight`/`divergence_weight`; built to test the "hot player stays hot" question directly). All four reuse `projections._game_log`'s exact leakage boundary. Unlike `usage_trend` before B5, all three trend fields (`usage_trend`/`momentum`/`divergence`) are also parseable from a live `weekly/week-NN.yml` (`week._parse_player_entry`), so a researcher can populate them outside a backtest too.
- **`ffbot/history/board.py`** — The historical parallel to `ffbot.board.load_board`, for B4's draft simulator. Two ingredients: positional rank from the latest FantasyPros PRESEASON cheatsheet scrape before week 1 (distinct from `projections.py`'s ROS pages — same `ecr_type == "rp"` archive, different page set), and ADP/stdev from Fantasy Football Calculator's free JSON API (`fetch.Source(format="json")`/`fetch_json`, ~150-210 players/season — see docs/BACKTEST.md's open questions for the coverage gap against the ECR-derived board's 800+). Rank → points is a SEASON-total calibration curve fit on other seasons only, same look-ahead guard as `ecr_projections`. Reuses `board.derive_replacement`/`assign_tiers` completely unchanged. `BoardPlayer.name`/`.team` deliberately carry the ORIGINAL display casing/team from the source rows, not the lowercased `actuals_key` used for matching — getting this backwards was a real bug caught by `tests/test_history_board.py::test_player_names_preserve_display_casing_not_normalized`.
- **`ffbot/backtest/`** — The evaluation layer built on `ffbot/history/`'s data layer; see the package's own `__init__.py` docstring for the one hard rule (ground truth only through `actuals.week_actuals`, never `WeekSnapshot.game_rows` directly). `rosters.py` samples seeded synthetic rosters from a fixed position mix rather than replaying a real draft — a deliberate B3 substitution to get enough statistical power out of only 4 clean ECR seasons; `draft_sim.py`/`season.py` (B4) provide the real-drafted-roster check, though that comparison hasn't been RUN yet (see docs/BACKTEST.md's open questions). `baselines.py` builds all five lineups (oracle/control/agent/consensus/random_legal) from the identical sampled roster, which is what makes the agent-vs-control comparison a true paired A/B. `metrics.py` implements docs/BACKTEST.md's statistics protocol exactly (paired deltas, discordant-pair extraction, block-bootstrap CI over `(season, week)`, plus B4's `paired_win_rate_deltas`) and nothing extra. `replay.py` is the runner `scripts/backtest_lineup.py` drives. `draft_sim.py` generalizes `tests/test_edge.py`'s single-manager `_simulate()` to N managers (one via `draft.recommend()`, the rest by noisy ADP) — its "opponents must never route through `recommend()`" warning carries over verbatim, since `recommend()` applies the AGENT's own caps/targets against the AGENT's own roster. `season.py` replays a full season for ONE manager under either policy (lineup + real `week.waiver_candidates` every week, rolling-priority tracked, roster mutated forward) against static reference opponents (frozen roster, greedy lineup, no waivers of their own) — a deliberate simplification to avoid needing 12 independently-tuned agents, documented as a real fidelity gap in docs/BACKTEST.md, not hidden. `schedule.py` is a round-robin scheduler (circle method, cycles past its natural length for `regular_season_weeks > num_teams - 1`) + win-loss records.

## Design invariants worth preserving

- **Config, not code, for tuning.** New thresholds/weights belong in `config.yml` + the corresponding dataclass in `ffbot/config.py`, not hardcoded.
- **The optimizer must stay exact and deterministic.** Any change to `ffbot/lineup.py` should preserve: (1) exact optimality (not a heuristic), (2) stable output across runs (ties break on player name), (3) minimal-move preference among equally optimal assignments. Both the in-season path and the draft assistant depend on this.
- **Drops are the one in-season action guarded by explicit policy**, not a confirmation step, because the agent is meant to act unattended. New irreversible actions should get the same treatment: a `Verdict`-returning policy function with the reason surfaced, not a silent allow/deny.
- **`scripts/draft.py`, `scripts/week_report.py`, and `scripts/gui.py` must stay importable and runnable with no network at module level.** `ffbot.sleeper`/`ffbot.sleeper_roster`/`ffbot.projections.sleeper` are all imported lazily, inside the function that actually needs them (`_build_sync`, `report.load_everything`'s live branches, `board.load_board_from_config`'s overlay branch) — the offline paths must keep working with no network at all, not just "no credentials." `week_report.py`'s own research step (weather/injuries/Vegas) is deliberately kept *outside* the script entirely, in the `/gameday` command — see `ffbot/week.py`'s module docstring.
- **Every live network call takes an injectable `opener`/client, and every fetch failure degrades gracefully with a surfaced alert — never a silent success and never a crash.** This is the same contract across every live seam in the repo: `ProjectionSourceConfig`'s `"sleeper"`, `RosterSourceConfig`'s `"sleeper"`, `DraftConfig.board_points_source`'s `"sleeper"`, and `ffbot.draft_sync.DraftSync`'s poll loop. A test asserting this must exist for any new live seam, matching `tests/test_history_index.py::TestAsOfLeakageGuarantee`'s pattern of proving it structurally, not just by inspection.
- **Pre-draft ID matching vs. live TUI search are different problems** (see `ffbot/names.py` above) — don't collapse them into one matcher.
- **Season-long valuation always passes `week=None`** to `optimize()` — `draft.need()` is always a season-long decision. `week.waiver_candidates()`/`rank_streamers()` now accept an optional real `week` too, but only to zero/exclude a candidate's *this-week* contribution when they're on bye that week — the rest-of-season side of any blend stays on the season board (or `ros_board`, when live) and must never be zeroed by it. Weekly *lineup* decisions (`week.build_week_brief`) are the one place a real week number was always correct and required.
- **A `Board`'s `points` overlay (`_apply_points_overlay`/`rescale_board_points` in `ffbot/board.py`) must run AFTER `apply_league_scoring`, never folded into the CSV/row merge ahead of it.** A merged-in `stats` field from an untouched source silently lets `apply_league_scoring`'s recompute clobber the overlay's live number right back to the frozen data it was meant to replace — a real bug this repo shipped and caught once already (see `ffbot/board.py`'s docstring on `_apply_points_overlay` and the regression test named in the Draft assistant path section above).
- **`scripts/gui.py` is single-threaded on purpose.** The draft session is one shared, mutable `UiState` with no lock — serializing every HTTP request through one thread (`http.server.HTTPServer`, not `ThreadingHTTPServer`) is what keeps `DraftState` main-thread-only (see `ffbot/draft_sync.py`'s existing invariant on this) without adding one. Don't switch it to a threading server without adding real synchronization.
- **`config.yml` is never rewritten by code.** It's hand-narrated with comments a YAML round-trip would destroy. Anything that needs to *write* settings (the GUI's Settings page) writes to the gitignored `config.local.yml` overlay instead (`_deep_merge`d on top at load time) — never add a code path that calls `yaml.safe_dump` against `config.yml` itself.
- **Historical replay must go through `ffbot.history.index.as_of()`.** No backtest code may read a historical data file (`data/history/*.csv`) directly — `as_of()` is the single point-in-time boundary, and its leakage guarantee (never fetching a results-bearing source) only holds if every caller actually goes through it. See [docs/BACKTEST.md](docs/BACKTEST.md)'s leakage register.
- **A rank→points (or any) calibration used for historical projections must be fit on seasons other than the one being graded.** `ffbot.history.projections.ecr_projections` enforces this by raising, not just documenting it — fitting on the test season is the single most likely way to fake a good backtest result.
- **`ffbot/backtest/` may read realized outcomes only through `ffbot.history.actuals.week_actuals`, never `WeekSnapshot.game_rows` directly.** `game_rows` is `ffbot.history.index`'s own separate post-hoc-scoring channel; routing every grading read through one function keeps "did a decision accidentally see the answer" a one-place-to-check question.
- **A `SignalProvider` (`ffbot/history/signals.py`) must never be folded into `as_of()` itself.** `as_of()`'s leakage guarantee is that it never fetches a results-bearing source at all — a provider that needs `stats_player_week` (even read leakage-safely, strictly before the target week) stays outside that boundary and merges in afterward via `WeekSnapshot.with_signals()`. Don't "simplify" this by moving a provider's fetch inside `as_of()`; that's exactly the exception the guarantee exists to never need.
